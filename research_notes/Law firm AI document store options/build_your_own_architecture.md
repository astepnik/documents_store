# Build-it-ourselves: reference architecture, sizing, cost and effort for a self-hosted, AI-friendly law-firm document store (as of November 2026)

Scope note: this file covers only the "build our own" option — data model, deterministic ingestion pipeline, hybrid search, access control, agent (MCP) access, hardware/hosting and engineering effort. SaaS vendors and open-source DMS products are evaluated by other researchers; open-source components are named here only as building blocks.

Research-method caveat: during this session most primary vendor domains (openai.com, cohere.com, ai.google.dev, docs.voyageai.com, qdrant.tech, hetzner.com, huggingface.co, docs.opensearch.org, modelcontextprotocol.io, runpod.io, cloudnine.com, edrm.net, arxiv.org) could not be fetched directly (network allow-list), so figures from those sources were obtained through search-engine excerpts and are marked "via search excerpt". github.com and blog.modelcontextprotocol.io were fetchable. Where only aggregator sites were available, that is stated. All derived arithmetic is shown and labelled.

## Reference architecture (synthesis — what to build)

### Takeaway
A single well-specified server (or one dedicated rented server plus a cold standby) can hold the whole system at 100–500 GB raw: object/file store for originals, Postgres for metadata + ACLs + audit, a BM25 engine (OpenSearch, or Postgres with pg_search/ParadeDB), a vector index (Qdrant, pgvector/pgvectorscale, or OpenSearch k-NN with quantization), a deterministic ingestion pipeline (connectors → extraction/OCR → chunking → embedding → indexing), and a thin API layer that exposes the same permission-filtered search to a web UI and to agents via MCP (Streamable HTTP, OAuth 2.1).

### Cited Findings (components and the facts that justify them)
- BM25 + vectors + RRF in one Postgres: "the easiest and most performant option for BM25 in Postgres is the ParadeDB pg_search extension", with pgvector for semantic similarity and Reciprocal Rank Fusion (1/(k+rank), k≈60) to merge — [ParadeDB, Hybrid Search in PostgreSQL: The Missing Manual](https://paradedb.com/blog/hybrid-search-in-postgresql-the-missing-manual); alternatives pg_textsearch, psql_bm25s, vchord_bm25 — [awesome-search](https://frutik.github.io/awesome-search/Topics/Search-using-PostgreSQL). pg_search versions in guides range 0.23.x (PG17) to 0.25.x — [pgxn docs](https://api.pgxn.org/src/pg_search/pg_search-0.25.3/docs/documentation/hybrid/overview.mdx).
- Disk-based / quantized vector search in OpenSearch: default compression_level 32x (binary quantization), two-phase search with rescoring from full-precision vectors on disk, default oversample_factor 3.0 at 32x; OpenSearch ≥3.1 adds "memory-optimized search" (on_disk mode at 1x loads data on demand) — [OpenSearch docs, disk-based vector search](https://docs.opensearch.org/docs/vector-search/optimizing-storage/disk-based-vector-search) (via search excerpt).
- Qdrant memory rule: memory ≈ 1.5 × vectors × dims × 4 bytes (1.5 = HNSW overhead); scalar int8 gives ~4x, binary ~32x reduction; Qdrant keeps originals alongside quantized vectors by default, so originals must be moved to disk/mmap to realise savings — [Qdrant capacity planning](https://qdrant.tech/documentation/cloud/capacity-sizing/) and [Qdrant quantization article](https://qdrant.tech/articles/what-is-vector-quantization/index.md) (via search excerpt).
- Embedding serving: Hugging Face Text Embeddings Inference (TEI) supports Qwen3 (0.6B/4B/8B), NomicBERT (nomic-embed v1/v1.5/v2-moe), JinaBERT, XLM-RoBERTa (multilingual-e5-large-instruct), BERT family, Gemma3, ModernBERT; ships CPU images (x86_64/aarch64, ONNX "ort" feature) and GPU images; dtype float16/float32 — [TEI README](https://github.com/huggingface/text-embeddings-inference) (fetched). For Qwen3-Embedding models vLLM was 2.6x (0.6B) faster than TEI in bulk embedding; for bge-m3, TEI and vLLM roughly tied (median 1.08x) — [Runpod GPU embedding benchmark](https://www.runpod.io/blog/gpu-embedding-workloads-benchmark) (via search excerpt).
- Agent access via MCP: the 2026-07-28 spec is stateless Streamable HTTP with OAuth 2.1 resource-server semantics (details in the MCP section below) — [MCP blog, 2026-07-28 release candidate](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/) (fetched).
- Access control pattern: "executing access filtering before vector similarity search" is "the single most important design decision" in a law-firm RAG system; the index is tagged with matter IDs and wall metadata and the wall is enforced at the database query level, not only in the application — [n8nlab, RAG system for law firms](https://n8nlab.io/blog/rag-system-law-firms).

### Inferences
- Recommended minimal stack for this scale: (1) originals on local NVMe/ZFS or MinIO; (2) Postgres 17 as system-of-record for documents, chunks, people/clients/matters, ACL/wall tables and the audit log; (3) either "Postgres-only" (pgvector/pgvectorscale + pg_search) for simplest ops, or Postgres + Qdrant (vectors) + OpenSearch (BM25 + DLS) when >20–50M chunks and heavier query load; (4) TEI or vLLM serving one open-weight embedding model on one GPU; (5) a FastAPI/Go search service that applies the identity-derived filter to both BM25 and vector queries, fuses with RRF, and is wrapped by an MCP server and a web UI.
- The deterministic requirement (no LLM calls in ingestion) is fully satisfiable: text extraction (Apache Tika / unstructured / pdfplumber), OCR (Tesseract or PaddleOCR), rule-based chunking, and a local embedding model are all deterministic given fixed versions; the only non-deterministic risk is model/version drift, which must be pinned (see re-embedding in the effort section).

### Gaps
- No single published reference architecture specifically for a law-firm self-hosted hybrid search was found; the above is a synthesis.

## Key question 1 — Sizing: raw bytes → text, documents, pages, tokens, chunks

### Takeaway
Industry heuristics put a "typical" GB of mixed office/e-mail data at 50,000–100,000 pages (75,000 common) and ~18,750–21,000 documents, but image-heavy data is ~15,000 pages/GB and plain text ~680,000 pages/GB, so 100 GB can mean anywhere from ~3M to ~10M pages. Converting at ~450–700 tokens/page gives roughly 1.5–7 billion tokens, i.e. about 3–15M chunks at 512 tokens or 6–30M at 256 tokens; the "20–50M chunks" planning figure in the brief corresponds to the high-token/small-chunk end at 100 GB or to the 500 GB growth case at 512 tokens.

### Cited Findings
- Pages per GB rule of thumb: "page per GB estimates tend to range from 50,000 to 100,000 pages per GB, so 75,000 pages (18,750 documents) seems an appropriate average" (assumes 4 pages/document) — [CloudNine eDiscovery Daily](https://cloudnine.com/ediscovery-best-practices-the-number-of-pages-in-each-gigabyte-can-vary-widely/) (via search excerpt). Older data (2007–2012).
- UK judiciary e-disclosure cost model uses 75,000 pages/GB and 3.5 pages/document — [judiciary.uk Appendix 19](https://www.judiciary.uk/wp-content/uploads/JCO/Documents/Guidance/app19.pdf) (via search excerpt).
- By file type (LexisNexis/Applied Discovery table, 2007): ~64,782 pages/GB for Word, ~100,099 for e-mail, ~677,963 for text files, ~15,477 for images, ~17,552 for PowerPoint — [CloudNine](https://cloudnine.com/ediscoverydaily/electronic-discovery/the-number-of-pages-in-each-gigabyte-can-vary-widely-ediscovery-replay/) and [Exterro](https://www.exterro.com/resources/blog/e-discovery-fact-week-day-four-examining-e-discovery-data-volumes) (via search excerpt). Vendors stress that GB-based figures give only a "ballpark" and a document count is needed for definitive estimates — [CloudNine](https://cloudnine.com/?p=174); [EDRM mirror](https://edrm.net/?p=32998).
- Enron / EDRM corpus: Nuix describes the EDRM v2 PST set as "almost 40 GB", 168 PST files, "1.3 million email messages and attachments" — [Nuix case study](https://de.slideshare.net/nuixdata/case-study-nuix-edrm-enron-data-set); a Hugging Face republication lists 1,226,178 messages and 453,832 attachments in 171 PSTs (source corpus 1,227,193 messages, 492,979 attachments) — [intellekthq/enron-ferc-pst](https://huggingface.co/datasets/intellekthq/enron-ferc-pst); a 2017 study found attachments take ~91% of disk space while only ~24% of messages carry attachments — [arXiv 1709.00362](https://arxiv.org/pdf/1709.00362.pdf) (all via search excerpt). Craig Ball (EDRM, Aug 2025) argues the corpus (2001 data) is "frozen in time" and not representative of modern collections (Teams, Slack, linked attachments) — [EDRM, Still on Dial-Up](https://edrm.net/2025/08/still-on-dial-up-why-its-time-to-retire-the-enron-email-corpus/); CloudNine notes the set is "not indicative of a typical eDiscovery email collection today" — [CloudNine](https://cloudnine.com/?p=19465).
- Tokens per page: ~0.75 words/token means a 500-word page ≈ 667 tokens — [TinyFish](https://www.tinyfish.ai/blog/what-is-a-token-in-ai-how-tokens-work-and-cost); legal documents are often cited at 300–350 words/page (≈400–470 tokens) — [wordcountertool](https://www.wordcountertool.net/blog/how-many-words-per-page); one source claims a legal contract page is 1,200–1,800 tokens — [iternal.ai](https://iternal.ai/token-usage-guide) — this conflicts with the former and is not reconciled by any source found.
- E-mail deduplication basis: the hash is built from metadata fields such as sender, sorted To/Cc/Bcc, UTC sent time, subject, body text, and attachment names/sizes/MD5s; attachments are kept as separate family-level records — [ediscoveryplatform.com technical note](https://sites.google.com/a/ediscoveryplatform.com/help/home/technical-notes-available/duplicates); [OpenText](https://blogs.opentext.com/what-counts-as-a-duplicate-in-your-ediscovery-software); near-duplicate detection uses similarity scores (e.g. 90%) and thread analysis suppresses redundant chain members — [GoldFynch](https://goldfynch.com/blog/2025/02/21/understanding-and-managing-different-types-of-duplicates-in-ediscovery.html); [CloudNine threading](https://cloudnine.com/ediscoverydaily/electronic-discovery/organize-your-collection-by-message-thread-to-save-costs-during-review-ediscovery-best-practices/). No typical dedup-rate percentage was found.

### Inferences (derived sizing — assumptions labelled)
Assumption A1: ~4 characters/token for English/European text (standard BPE rule of thumb, no primary source fetched). Assumption A2: chunk overlap adds ~10–15% to chunk count. Assumption A3 (unsourced engineering rules of thumb — verify by sampling your own data): raw→plain-text byte ratios ≈ DOCX 10–20%, born-digital PDF 5–20%, scanned PDF/TIFF 0.1–1% (a 300-dpi page image of 50–150 KB yields ~2–4 KB of text), e-mail body 30–60% of message bytes excluding attachments (text/plain + text/html alternatives and MIME overhead inflate bytes).

Pages and documents for 100 GB (from cited heuristics):
- Text/e-mail-heavy mix at 75,000 pages/GB → 7.5M pages; at 18,750 docs/GB → ~1.9M documents (UK model: 75,000/3.5 ≈ 21,400 docs/GB → 2.1M documents).
- Scan-heavy mix (e.g. 50% images at 15,500 pages/GB + 50% office/e-mail at 80,000) → (0.5×15,500 + 0.5×80,000) ≈ 47,750 pages/GB → ~4.8M pages.
- Extremes: all-image 1.5M pages; all e-mail ~10M pages.

Tokens (pages × tokens/page):
- Low: 3M pages × 450 = 1.35B tokens. Central: 7.5M × 600 = 4.5B tokens. High: 10M × 700 = 7B tokens.
- Cross-check via text ratio (A3): 100 GB × 5–20% text = 5–20 GB text ≈ 1.25–5B tokens at 4 chars/token — consistent with the page-based range.

Chunks (tokens ÷ chunk size × 1.15 overlap, A2):
| Corpus | Tokens | 256-tok chunks | 512-tok chunks | 1024-tok chunks |
|---|---|---|---|---|
| 100 GB low | 1.35B | 6.1M | 3.0M | 1.5M |
| 100 GB central | 4.5B | 20M | 10M | 5M |
| 100 GB high | 7B | 31M | 16M | 8M |
| 500 GB central | 22.5B | 100M | 50M | 25M |

Planning recommendation: design for ~10M chunks (512 tokens) at 100 GB and ~50M at 500 GB; if 256-token chunks are chosen, double these. Document-level metadata rows (~2M at 100 GB, ~10M at 500 GB) are trivial for Postgres.

E-mail-specific: Enron's 40 GB / 1.23M messages ≈ 31,000 messages/GB including attachments (derived from the Nuix and Hugging Face figures), with ~37% of messages having attachments by count (453,832/1,226,178) but attachments ≈ 91% of bytes. For a 50 GB mailbox export, expect on the order of 1–1.5M messages; dedup across mailboxes (same message in sender's Sent Items and each recipient's Inbox) will remove a substantial fraction — no reliable percentage was found, treat 30–60% reduction as a hypothesis to measure.

### Gaps
- No 2024–2026 refresh of pages/documents-per-GB statistics was found; all industry figures date from 2007–2012.
- No published raw-bytes→extracted-text ratios per file type were found; A3 is unsourced.
- No published typical e-mail deduplication rate was found.

## Key question 2 — Embedding throughput (local GPU/CPU) and API costs

### Takeaway
On a workstation/datacenter Ada-class GPU, bge-m3 (568M params) embeds ~190–275 texts/s at 512 tokens (RTX A5000 ~190, RTX A6000 ~265, RTX 6000 Ada ~275; H100 ~1,240) under TEI, so 10M chunks take ~10–15 GPU-hours and 50M chunks ~2–3 GPU-days on one Ada card; API embedding of a 4.5B-token corpus costs roughly $90 (OpenAI 3-small) to ~$600–900 (voyage-law-2, gemini-embedding) one-off, before re-embedding cycles.

### Cited Findings
- Runpod benchmark (bge-m3, 512-token passages, TEI): ~190 texts/s RTX A5000, ~265 RTX A6000, ~275 RTX 6000 Ada, ~1,240 H100 SXM, ~1,345 H200; cost per billion input tokens e.g. $1.53 on H100 SXM at Runpod rates — [Runpod GPU embedding benchmark](https://www.runpod.io/blog/gpu-embedding-workloads-benchmark) (via search excerpt; no RTX 4090/5090, L4, L40S, A10 figures were in the excerpt). Same post: vLLM 2.6x faster than TEI for Qwen3-Embedding-0.6B; TEI≈vLLM for bge-m3.
- TEI README benchmark is for bge-base-en-v1.5 on an NVIDIA A10 at 512 tokens, batch 1 and 32, presented only as charts (no numeric values in text) — [TEI README](https://github.com/huggingface/text-embeddings-inference) (fetched).
- Baseten: Qwen3-Embedding on B200 (BEI) gave 3.3x the throughput of vLLM and 3.6x of TEI on H100 at 500 tokens/request — [Baseten blog](https://baseten.co/blog/run-qwen3-embedding-on-nvidia-blackwell-gpus) (via search excerpt).
- Model specs: Qwen3-Embedding-0.6B: 596M params, up to 1024 dims (MRL 32–1024), 32K context, Apache 2.0, MTEB(Multilingual) 64.33, MTEB(English v2) 70.70 — [Modal model page](https://modal.com/library/qwen/qwen3-embedding-0-6b); [Accenture catalog](https://sdk.airefinery.accenture.com/distiller/model_catalog/Embedding/Qwen/Qwen3-Embedding-0.6B/). BGE-M3: ~568M params, 1024 dims, 8,192-token context, dense+sparse+multi-vector — [SurrealDB comparison](https://surrealdb.com/blog/embedding-models-comparison). snowflake-arctic-embed-l-v2.0: 303M params, 1024 dims, MTEB-Retrieval 0.556 vs multilingual-e5-large 0.514 (303M, 1024) and BGE-M3 0.488 (same table) — [Arctic-Embed 2.0 paper](https://arxiv.org/pdf/2412.04506). jina-embeddings-v3: 570M params, beats multilingual-e5-large-instruct on all multilingual MTEB tasks — [jina v3 paper](https://www.arxiv.org/pdf/2409.10173). nomic-embed-text v1.5: 138M params; v2-moe: 475M total / 305M active, 768 dims (MRL to 256) — [SurrealDB comparison](https://surrealdb.com/blog/embedding-models-comparison).
- CPU: only relative speedups found. Neural Magic/DeepSparse INT8 bge-base: "up to 4.5X" latency improvement on a 16-core AWS instance vs baseline (baseline unspecified) — [neuralmagic/bge-base-en-v1.5-quant](https://huggingface.co/neuralmagic/bge-base-en-v1.5-quant); Manticore reports an ONNX backend ~14x faster than its previous SentenceTransformers/Candle path on a 16-core/32-thread server — [Manticore blog](https://manticoresearch.com/blog/onnx-embeddings-speedup). No absolute sentences/s figure for a 16-core CPU was found.
- API prices (vendor pages not fetchable; aggregator figures): OpenAI text-embedding-3-small $0.02/M tokens, text-embedding-3-large $0.13/M, Batch API halves both — [costbench OpenAI embeddings](https://costbench.com/software/embedding-apis/openai-embeddings/); [rework comparison](https://resources.rework.com/tools/ai-data-infra/best-embedding-models-2026). Voyage (official page via search excerpt): voyage-4 $0.06/M, voyage-4-large $0.12/M, voyage-4-lite $0.02/M, voyage-law-2 $0.12/M, voyage-code-4 $0.12/M; first 200M tokens free for voyage-4 family/voyage-context-4, first 50M free for voyage-law-2/finance-2/multilingual-2 — [Voyage pricing](https://docs.voyageai.com/docs/pricing); Batch API 33% discount (third party) — [costbench Voyage](https://costbench.com/software/embedding-apis/voyage-ai/). ### Inferences (derived — assumptions labelled)
GPU time for bge-m3-class (≈0.5–0.6B param) models, 512-token chunks:
- RTX 6000 Ada ≈ 275 chunks/s ≈ 141k tokens/s (275×512). 10M chunks ÷ 275 = 36,400 s ≈ 10.1 h; 20M → 20 h; 50M → 50 h ≈ 2.1 days. H100 (1,240/s): 10M → 2.2 h; 50M → 11 h.
- Assumption B1: RTX 4090 / L40S are the same Ada generation as RTX 6000 Ada and should land in a similar 200–350 texts/s band; RTX 5090 (Blackwell, GDDR7) plausibly 1.3–2x that; L4 and A10 (lower-power) likely 60–150 texts/s. These are extrapolations, not measurements — benchmark before committing.
- Smaller models (multilingual-e5-large 303M, arctic-embed-l-v2 303M) should be ~1.5–2x faster than bge-m3 at equal sequence length (parameter-count scaling, assumption); Qwen3-Embedding-4B/8B will be ~6–14x slower than 0.6B and only make sense with vLLM on a 24–48 GB card; nomic v1.5 (138M) ~3–4x faster than bge-m3.
- CPU (assumption B2, unsourced): a 16-core server running ONNX int8 might sustain ~10–40 bge-m3 chunks/s at 512 tokens → 10M chunks = 70–280 hours (3–12 days). Viable for a one-off initial load if a GPU is unavailable, and sufficient for incremental daily volume (a firm adding e.g. 5,000 documents/day ≈ 25k chunks/day ≈ 20 min at 20/s), but a GPU is strongly preferable for re-embedding cycles.
- API cost for the corpus (central 4.5B tokens; low 1.35B; 500 GB ≈ 22.5B):
  | Model | $/M | 1.35B | 4.5B | 22.5B |
  |---|---|---|---|---|
  | OpenAI 3-small ($0.02; $0.01 batch) | 0.02 | $27 ($14) | $90 ($45) | $450 ($225) |
  | OpenAI 3-large ($0.13; $0.065 batch) | 0.13 | $176 ($88) | $585 ($293) | $2,925 ($1,463) |
  | Voyage voyage-4 ($0.06, 200M free) | 0.06 | $69 | $258 | $1,338 |
  | Voyage voyage-law-2 ($0.12, 50M free) | 0.12 | $156 | $534 | $2,694 |

- Local-GPU cost comparison: a rented GPU server at ~€212/month (Hetzner GEX44, see hardware section) embeds the whole 100 GB corpus in ~1–2 days of wall time, so on-prem embedding is in the tens of euros of amortised compute per full pass; the GPU's real cost is its idle time, which is why it should double as the query-time embedding/reranking server.

- Vendor pricing pages were not fetchable; Cohere and Google figures rest on aggregators and should be re-checked.

## Key question 3 — Storage: vector index size, HNSW RAM, disk-based alternatives, engine choice

### Takeaway
At 1024 dims, 10M float32 vectors are ~41 GB raw and ~61 GB in RAM as an HNSW index (Qdrant's 1.5x rule); 50M is ~205 GB raw / ~307 GB in RAM — too much for a cheap single box in float32, but int8 (÷4) or binary (÷32) quantization with on-disk originals brings 50M vectors to ~77 GB or ~10 GB RAM respectively, so a single 128–256 GB server comfortably serves 20–50M chunks with any of pgvector/pgvectorscale, Qdrant or OpenSearch.

### Cited Findings
- Qdrant: memory_size = N × D × 4 bytes × 1.5; worked example 1M × 1024-d ≈ 5.72 GB (1.5 covers HNSW graph); scalar quantization = 75% less per number; binary ≈ 32x reduction; originals kept by default (negates savings unless moved to disk); mmap storage keeps hot vectors in RAM — [Qdrant capacity planning](https://qdrant.tech/documentation/cloud/capacity-sizing/); [Qdrant scalar quantization](https://qdrant.tech/articles/scalar-quantization/) (via search excerpt).
- OpenSearch memory formulas: 1-bit (binary) HNSW ≈ 1.1 × (D × bits/8 + 8 × m) bytes/vector (example: 256-d, m=16 ≈ 0.176 GB per 1M vectors) — [OpenSearch Faiss scalar quantization](https://docs.opensearch.org/latest/vector-search/optimizing-storage/faiss-scalar-quantization/); fp16 (SQfp16) ≈ 1.1 × (2D + 8m) bytes/vector (2.15 docs) and "50% of the memory" of fp32 — [OpenSearch 2.15 quantization](https://docs.opensearch.org/2.15/search-plugins/knn/knn-vector-quantization); Lucene scalar quantization ≈ ¼ memory of fp32, but disk usage rises since raw + quantized are both stored — [OpenSearch Lucene SQ](https://docs.opensearch.org/docs/vector-search/optimizing-storage/lucene-scalar-quantization); disk-based mode: 32x default compression, rescoring with oversample 3.0, "slightly increased search latency" — [OpenSearch disk-based](https://docs.opensearch.org/docs/vector-search/optimizing-storage/disk-based-vector-search) (all via search excerpt).
- pgvector: HNSW build must hold the whole graph in memory; rough build-memory rule N × D × 4 × 2 (≈60 GB for 5M × 1536-d); maintenance_work_mem default 64 MB, recommended 8–16 GB for builds, otherwise a disk-based build runs "10–50x slower" — [dev.to, Scaling pgvector](https://dev.to/philip_mcclarence_2ef9475/scaling-pgvector-memory-quantization-and-index-build-strategies-8m2); [dev.to, choosing a pgvector index](https://dev.to/multigrid/choosing-and-tuning-a-pgvector-index-1hki). Estimates for 10M × 1536-d HNSW range 60–120 GB across blogs (unverified) — [selfhost.dev pgvector 2026 reality check](https://www.selfhost.dev/blog/pgvector-in-production-2026-critiques-failures/). Alibaba's RDS test shows build time stops improving once maintenance_work_mem exceeds the dataset size — [Alibaba Cloud pgvector HNSW test](https://www.alibabacloud.com/help/en/rds/apsaradb-rds-for-postgresql/pgvector-performance-test-based-on-hnsw-indexes).
- pgvectorscale (StreamingDiskANN, Statistical Binary Quantization): on 50M Cohere 768-d embeddings, "28x lower p95 latency and 16x higher query throughput compared to Pinecone's storage optimized (s1) index"; stores part of the index on disk — [timescale/pgvectorscale README](https://github.com/timescale/pgvectorscale); [TigerData blog](https://www.tigerdata.com/blog/pgvector-is-now-as-fast-as-pinecone-at-75-less-cost). A third-party write-up cites 471 QPS at 99% recall on 50M × 1536-d (vendor-sourced) — [Towards AI](https://pub.towardsai.net/i-benchmarked-pgvector-vs-qdrant-vs-pinecone-on-50m-vectors-postgres-crushed-the-dedicated-dbs-by-20aa6dcdf132). halfvec roughly halves index footprint with negligible recall loss; binary + rerank costs ~5–10% recall without rerank — [callsphere](https://www.callsphere.ai/blog/vw6g-pgvector-hnsw-quantization-scale-2026) (weak source).
- Qdrant HA: a single node cannot be redundant (no two replicas of a shard on one node); HA needs ≥3 voting nodes and replication factor ≥2; snapshots (local or S3) are the backup/DR mechanism and can restore missing shards — [Qdrant resilience](https://qdrant.tech/documentation/scaling/resilience/); [Qdrant backups](https://qdrant.tech/documentation/cloud/backups/index.md) (via search excerpt).

### Inferences (derived)
Raw vector bytes = N × D × 4 (fp32):
| N chunks | 768-d fp32 | 1024-d fp32 | 1024-d int8 | 1024-d binary |
|---|---|---|---|---|
| 10M | 30.7 GB | 41 GB | 10.2 GB | 1.28 GB |
| 20M | 61 GB | 82 GB | 20.5 GB | 2.6 GB |
| 50M | 154 GB | 205 GB | 51 GB | 6.4 GB |

HNSW RAM (Qdrant 1.5x rule): 10M×1024-d fp32 ≈ 61 GB; 20M ≈ 123 GB; 50M ≈ 307 GB. int8 in RAM with fp32 on disk: 10M ≈ 15 GB, 50M ≈ 77 GB. Binary in RAM (OpenSearch formula, D=1024, m=16: 1.1×(128+128)=282 B/vector): 10M ≈ 2.8 GB, 50M ≈ 14 GB, plus fp32 on NVMe for rescoring (205 GB at 50M). fp16 (1.1×(2048+128)=2,394 B/vector): 10M ≈ 24 GB, 50M ≈ 120 GB.

Text side: BM25 inverted index for 5–20 GB of text is typically a similar order of magnitude to the text (assumption, no source) → budget 10–40 GB on disk for 100 GB raw; Postgres metadata for ~2M documents / ~10M chunk rows (with chunk text stored) ≈ text size + indexes ≈ 15–40 GB.

Engine choice at this scale:
- ≤20M chunks and a team that knows Postgres: pgvector (halfvec, HNSW) or pgvectorscale + pg_search in one Postgres on a 128 GB box; simplest backup (pg_dump/pgBackRest — not researched), single ACL model in SQL.
- 20–50M+ chunks or stricter latency/DLS needs: Qdrant (int8/binary with originals on disk, payload filters for client/matter/ACL) + OpenSearch (BM25 + document-level security) + Postgres for metadata. Still one physical server at 256 GB RAM; HA requires 3 Qdrant nodes, which argues for keeping an "active + cold standby restored from snapshots" posture rather than true HA at a small firm.
- Disk: originals 100–500 GB + fp32 vectors 41–205 GB + text/BM25/Postgres 30–80 GB + snapshots/backups ≈ 2–4 TB NVMe for the 500 GB growth case.

### Gaps
- No controlled, published memory measurement for pgvector HNSW at 10–50M vectors was found (only blog estimates).
- Qdrant's exact per-vector HNSW overhead at different M values and payload-index sizes were not retrievable (qdrant.tech unreachable).

## Key question 4 — Deterministic metadata model (client, matter, handler, case type) without an LLM

### Takeaway
Practitioner guidance converges on a matter-number-keyed folder hierarchy plus required metadata columns (Client Name, Matter Number) in SharePoint, short structured filenames (date | client | matter | abbreviation | description), and the recognition that conventions drift unless tooling enforces them; the deterministic design is therefore a rules engine that maps path/filename patterns, SharePoint columns and e-mail header fields to IDs from a practice-management export, with explicit confidence levels and an "unassigned" queue reviewed by humans.

### Cited Findings
- Matter-keyed containers: "every client engagement receives a dedicated matter container identified by a unique client-matter number" with subfolders (intake, corporate records, …) — [fast.io, Law office file management](https://fast.io/resources/law-office-file-management/); template "client name and number, matter name subfolder and then nested folders" for correspondence/discovery/filings — [Bill4Time, 5 file tree templates](https://www.bill4time.com/blog/5-file-tree-structure-templates-for-law-firms/).
- Numeric vs alphabetical: alphabetical suits boutiques, numerical scales better; some firms use matter numbers specifically to avoid sensitive information in filenames — [renamer.ai, legal file naming conventions](https://renamer.ai/insights/legal-file-naming-conventions); [NC Bar, DIY file naming](https://www.ncbar.org/2022/04/05/diy-file-naming-conventions-and-folder-structure/).
- Filename pattern "Date | Client | Matter | Abbreviation | Description", keep to 4–5 fields and let folders/metadata carry the rest — [Filevine](https://filevine.com/blog/steps-to-better-legal-file-conventions/); [renamer.ai](https://renamer.ai/legal-document-naming-convention); with a proper DMS "it doesn't matter" because metadata does the work — [LexWorkplace](https://lexworkplace.com/organize-legal-files/).
- SharePoint: core columns such as Client Name and Matter Number as required fields so documents in a set inherit properties — [fast.io, SharePoint law firm template](https://fast.io/resources/sharepoint-law-firm-template/).
- Drift: without a standard "everyone invents their own system"; tooling should apply the convention — [renamer.ai, law firm DMS](https://renamer.ai/law-firm-document-management).
- E-mail identity fields usable deterministically (the same fields e-discovery uses for dedup hashing): sender, sorted To/Cc/Bcc, UTC sent time, subject, attachment names/sizes/MD5 — [ediscoveryplatform.com](https://sites.google.com/a/ediscoveryplatform.com/help/home/technical-notes-available/duplicates); attachments as family-level child records — [OpenText](https://blogs.opentext.com/what-counts-as-a-duplicate-in-your-ediscovery-software).
- Ethical-wall caveat relevant to the model: products that secure only at document/folder level may still expose the matter in a lookup table — [Kraft Kennedy, How solid is your DMS ethical wall](https://www.kraftkennedy.com/how-solid-is-your-dms-ethical-wall/).

### Inferences (proposed data model and assignment rules)
Core tables (Postgres): person (lawyers/staff; AD/Entra object id), client (PMS client id), matter (PMS matter id, client_id, case_type, responsible_lawyer_id, team members, open/close dates, wall_group), document (sha256, source system + source id/path/etag, mime, size, created/modified, extraction status, ocr flag, parser version), document_assignment (document_id, matter_id, client_id, role ∈ {primary, cc, related}, method ∈ {pms_link, path_rule, sharepoint_column, filename_code, email_domain, email_thread, manual}, confidence, rule_version, assigned_at) — many-to-many so multi-client/multi-matter documents are representable; email (message_id, in_reply_to, references, thread_id, from, to[], cc[], sent_utc, dedup_hash), attachment (parent email_id, document_id), chunk (document_id, ordinal, token_count, text, embedding_model_version, vector ref), acl/wall (matter_id or client_id, principal, allow/deny, source = Intapp/iManage/manual export), audit_log (actor, agent/client id, query, filters applied, result doc ids, timestamp).

Deterministic assignment cascade (highest confidence first):
1. PMS export as source of truth: nightly CSV/API export of clients, matters, case types, responsible lawyers and team membership; all other sources resolve to these IDs. (No source found describing PMS-export workflows; this is a design inference.)
2. SharePoint: library columns Client/Matter (required fields) → direct ID match; library/site per matter → site-to-matter mapping table.
3. File share: regex on path, e.g. `^/Clients/(?P<client>\d{5})/(?P<matter>\d{5}-\d{3})/` and on filenames containing the matter code; one rule set per share, versioned in git.
4. E-mail: (a) matter code in subject tag (e.g. `[12345-003]`) → match; (b) sender/recipient domain → client domain table (built from PMS contacts; ambiguous domains like gmail.com excluded); (c) thread inheritance: a reply/forward inherits the assignment of the thread root via In-Reply-To/References; (d) mailbox owner → handler (the custodian is the handler candidate, not necessarily the responsible lawyer).
5. Attachments inherit the parent e-mail's assignment with method=email_parent; identical attachment hashes found in a matter folder reinforce assignment.
6. Residual → "unassigned" queue with the top deterministic hints, surfaced in the UI for a paralegal to resolve; manual decisions are stored as rules where generalisable.
Auditability: store method, rule_version and confidence on every assignment; keep rules in version control; recompute assignments idempotently when rules change and diff the results. Avoid any LLM in the loop by design; if the firm later wants ML-assisted classification, keep it as a separate "suggestion" channel that writes method=ml_suggestion and never auto-publishes.

### Gaps
- No published description of deterministic client/matter assignment from e-mail headers or PMS exports was found; the cascade above is an inference from e-discovery dedup practice and DMS conventions.

## Key question 5 — Document-level access control, ethical walls and audit logging in the search layer

### Takeaway
All sources found agree the wall must be applied as a mandatory pre-retrieval filter at the index/database layer (not post-filtering in the application), with matter/wall metadata on every indexed chunk; OpenSearch's security plugin provides document-level security with an "adaptive" evaluation mode that runs simple term filters at Lucene level, and the practical caveat is that matter existence itself (lookup tables, facets, counts) can leak unless also filtered and that walls are respected "silently" unless you log them.

### Cited Findings
- Pre-filtering: "executing access filtering before vector similarity search" prevents restricted documents from pushing permitted ones out of the top-k; the index is "tagged with matter IDs and wall metadata"; "Ethical walls must be enforced at the database query level, not just the application layer" — [n8nlab, RAG for law firms](https://n8nlab.io/blog/rag-system-law-firms).
- Vendor practice (as a pattern, not a product evaluation): Harvey states permissions and ethical walls are "enforced at query time, not bolted on afterward" — [Harvey, Long-horizon agents and ethical walls](https://www.harvey.ai/en-US/blog/long-horizon-agents-and-ethical-walls); a consultancy case study reports restricted docs "filtered at vector store query level — never returned" with every query logged (self-reported) — [abstrsbit case study](https://abstrsbit-ai-portfolio.pages.dev/case-study-legal-rag%20(1).html).
- Pitfalls: "Vendors have been known to describe their products as having Ethical Walls, when in reality these products only provide security at the document or folder-level. The matter itself can still [be] exposed on a look-up table" — [Kraft Kennedy](https://www.kraftkennedy.com/how-solid-is-your-dms-ethical-wall/); a tool "respects the screen silently" without a user-facing log — [Intapp](https://www.intapp.com/?p=32876).
- Ecosystem: Intapp Walls and iManage Security Policy Manager are the established wall-policy systems; Lexsoft integrated its T3 search with both — [Legal IT Professionals](https://legalitprofessionals.com/global-news/14052-lexsoft-introduces-ethical-walls-capability-for-search-in-the-t3-legal-knowledge-management-solution); Intapp describes document- or matter-level security per central firm policies — [Intapp](https://www.intapp.com/?p=32876).
- OpenSearch DLS: default "adaptive" mode runs DLS queries without term-lookup queries (TLQ) at Lucene level ("most efficient") and TLQ-based ones in filter-level mode; configurable via plugins.security.dls.mode; docs recommend keeping DLS queries simple to limit performance impact — [OpenSearch DLS docs 3.5](https://docs.opensearch.org/3.5/security/access-control/document-level-security/); [OpenSearch DLS 2.6](https://docs.opensearch.org/2.6/security/access-control/document-level-security/); forum thread on DLS at scale with no measured numbers — [OpenSearch forum](https://forum.opensearch.org/t/document-level-security-at-scale/16834).
- MCP side: MCP Apps UI actions "go through the same consent and audit path as tool calls" (2026-07-28) — [MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/) (fetched).

### Inferences
- Filter-at-query-time vs separate indexes: with ~hundreds to low-thousands of matters and walls that change frequently, a single index with per-chunk `client_id`, `matter_id`, `wall_group` payload and a mandatory filter derived server-side from the caller's identity is the right default; separate indexes per client only make sense for a handful of ultra-sensitive matters (hard isolation, simpler audit) and multiply operational cost. Qdrant payload filters, pgvector `WHERE` clauses (with the HNSW iterative-scan / filtered-search behaviour tested at your selectivity) and OpenSearch DLS all support the pattern; test recall when filters are highly selective (filtered HNSW can degrade — not sourced here, verify).
- Default-deny: compute the allowed set as (firm-wide open matters) MINUS (walled matters for this principal) MINUS (matters restricted to a team the principal is not in); apply the same filter to facets, counts, autocomplete and "related matters" to avoid the lookup-table leak; return no distinguishable error for walled vs non-existent items.
- Wall source of truth: import from Intapp Walls / iManage SPM / PMS team membership on a schedule; store effective-from timestamps so audits can reconstruct who could see what when.
- Audit log for agents: log principal, acting client (Claude/ChatGPT/Copilot connector id), tool name, raw arguments, server-applied filter, returned document/chunk ids, latency, and token counts; retain per the firm's retention policy; alert on anomalous patterns (e.g. one agent session touching >N matters). None of this exists off-the-shelf in MCP; it is ~1–2 weeks of work in the API layer.

### Gaps
- No independent benchmark of query-time wall filtering overhead (OpenSearch DLS, Qdrant payload filters, pgvector) was found.
- No published audit-logging schema for agent search queries in legal settings was found.

## Key question 6 — Agent access via MCP in 2026

### Takeaway
The current MCP revision is 2026-07-28 (release candidate locked 21 May 2026, final 28 July 2026): stateless Streamable HTTP (no initialize handshake, no Mcp-Session-Id), mandatory Mcp-Method/Mcp-Name headers, a formal extensions framework (Tasks, MCP Apps), JSON Schema 2020-12 tool schemas, and OAuth 2.1 resource-server authorization (RFC 9728 protected-resource metadata, RFC 8707 resource indicators, RFC 9207 iss validation). ChatGPT, Claude and Microsoft 365 Copilot can all consume remote MCP servers, with different admin gating; the official Postgres reference server is reported archived and Elastic's server deprecated in favour of its Agent Builder endpoint, so a firm should write its own thin MCP server exposing a permission-filtered `search` tool rather than exposing a database directly.

### Cited Findings
- 2026-07-28 revision (fetched from the official blog): RC locked 21 May 2026, final 28 July 2026; version sent in `MCP-Protocol-Version` header; baseline compared is 2025-11-25. Removes initialize/initialized handshake (SEP-2575) — protocol version, client info and capabilities travel in `_meta`; new `server/discover`; removes `Mcp-Session-Id` (SEP-2567) so any instance can serve any request; requires `Mcp-Method`/`Mcp-Name` headers on Streamable HTTP (SEP-2243); `ttlMs`/`cacheScope` on list/read results (SEP-2549); W3C Trace Context in `_meta` (SEP-414); server-initiated requests only while processing a client request (SEP-2260); Multi Round-Trip Requests replace held-open SSE (SEP-2322); extensions framework (SEP-2133) with reverse-DNS ids; MCP Apps (SEP-1865) sandboxed HTML UIs; Tasks moved to an extension (`tasks/get|update|cancel`, `tasks/list` removed); authorization: clients MUST validate `iss` per RFC 9207 (SEP-2468), declare `application_type` in DCR (SEP-837), credentials bound to issuer (SEP-2352), refresh-token/step-up/.well-known clarifications (SEP-2207/2350/2351); deprecations (annotation-only, ≥12 months before removal): Roots, Sampling, Logging (SEP-2577); tool schemas full JSON Schema 2020-12 (SEP-2106); missing-resource error -32002 → -32602 (SEP-2164); conformance-suite scenario required for Standards Track SEPs (SEP-2484) — [MCP blog, 2026-07-28 release candidate](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/).
- Secondary commentary: the revision "harden[s] the authorization specification to align more closely with how OAuth 2.0 and OpenID Connect are deployed in practice"; integrates with Entra/Okta; one post describes an Enterprise-Managed Authorization (EMA) extension — [Descope, July 2026 MCP revision](https://www.descope.com/blog/post/july-2026-mcp-revision); [baeke.info](https://news.baeke.info/articles/mcp-2026-07-28-spec-drops-stateful-sessions-adds-oauth-and-extension-framework); [AAIF migration post](https://aaif.io/blog/mcp-2026-07-28-whats-changing-and-how-to-migrate). Statelessness "changes basically nothing about your auth" if you already follow the auth spec — [hyrax.dev](https://hyrax.dev/blog/mcp-2026-07-28-stateless-migration-auth-review).
- Prior revisions: 2025-06-18 made RFC 8707 resource indicators a client MUST (send `resource` in authorization and token requests) and replaced fallback endpoints with mandatory RFC 9728 Protected Resource Metadata on the MCP server; 2025-11-25 downgraded Dynamic Client Registration from SHOULD to MAY — [Keycloak MCP docs](https://www.keycloak.org/securing-apps/mcp-authz-server); [Auth0, MCP specs update](https://auth0.com/blog/mcp-specs-update-all-about-auth/); [WorkOS, MCP 2026 spec](https://workos.com/blog/mcp-2026-spec-agent-authentication). Keycloak's RFC 8707 support is "experimental" — [Keycloak](https://www.keycloak.org/securing-apps/mcp-authz-server). Transport history: HTTP+SSE deprecated March 2025, replaced by Streamable HTTP — [calmara MCP compatibility](https://calmara.app/mcp-compatibility).
- Client support: ChatGPT custom remote MCP via Developer Mode on Plus/Pro/Business/Enterprise/Edu (not Free); remote endpoints only ("cannot connect to localhost"); Enterprise/Edu admins get role-based access and a publish/review workflow; connectors renamed "apps" Dec 2025 — [Composio, ChatGPT custom connectors](https://composio.dev/blog/chatgpt-custom-connectors-connect-any-app-with-mcp); [obot.ai](https://obot.ai/resources/learning-center/chatgpt-mcp-support-enterprise/). Claude: custom MCP via Settings → Connectors, and can also run local stdio servers — [calmara](https://calmara.app/mcp-compatibility). Microsoft 365 Copilot: maker/admin only via Copilot Studio agent or Agent Store, no end-user paste-a-URL path — [calmara](https://calmara.app/mcp-compatibility). (Plan-eligibility details conflict across sources.)
- Reference servers: the reference Postgres server in modelcontextprotocol/servers is reported archived as of Oct 2026 (Postgres MCP Pro and pgEdge MCP Server, GA 2 April 2026, named as alternatives) — [Peliqan](https://peliqan.io/blog/postgres-mcp/); [pgEdge press release](https://www.pgedge.com/press-releases/pgedge-mcp-server-for-postgres-now-generally-available-including-in-pgedge-cloud-advancing-enterprise-ai-infrastructure); one directory still lists it as live with read-only defaults — [enterprisedna](https://enterprisedna.co/directories/mcp/mcp-postgres) (conflict; check the repo). Elastic deprecated its MCP server in favour of the Agent Builder MCP endpoint — [automationswitch](https://automationswitch.vercel.app/mcp-servers/elasticsearch-mcp). Qdrant has an official server (store/find by semantic search in a collection) — [automationswitch database category](https://automationswitch.vercel.app/mcp-servers/category/database).

### Inferences (how to expose search to agents)
- Build a purpose-built MCP server (Streamable HTTP, 2026-07-28, stateless) in front of the same search API the UI uses. Do not expose Postgres/Qdrant/OpenSearch MCP servers to agents: they bypass the wall filter and leak schema.
- Tools: `search_documents(query, filters{client_ids?, matter_ids?, case_types?, handler_ids?, date_from?, date_to?, doc_types?}, top_k, mode ∈ {hybrid, bm25, vector})`, `get_document(document_id, page_range?)`, `list_matters(client_id?)`, `get_thread(email_id)`. The identity-derived ACL filter is always ANDed server-side; agent-supplied filters only narrow. Mark `search_documents` read-only via tool annotations; keep result payloads small (ids, snippet, matter, score) and let `get_document` page through text to control token spend.
- Auth: run the server as an OAuth 2.1 resource server behind the firm's IdP (Entra ID/Okta/Keycloak), publish RFC 9728 metadata, require RFC 8707 audience-bound tokens, no DCR for internal use (pre-register the Claude/ChatGPT/Copilot clients), scopes like `docs.search`, `docs.read`. Map the token's subject to the firm's person record to derive the wall filter; log every call (see Q5).
- Expect to track spec revisions roughly yearly (2025-03-26 → 2025-06-18 → 2025-11-25 → 2026-07-28) and to migrate SDKs each time; budget ~1–2 engineer-weeks per revision.

### Gaps
- The official spec text at modelcontextprotocol.io was not fetchable; MUST/SHOULD details of the 2026-07-28 authorization section rest on the release-candidate blog and vendor summaries.
- No authoritative Microsoft documentation on Copilot Studio MCP configuration/governance was retrieved.

Compared with 2024 this is roughly double because of DRAM.

Data residency: Hetzner (DE/FI), OVH (FR/UK/CA/…); check professional-conduct rules for client data in a third-party datacenter — a rented dedicated server is single-tenant hardware but not on the firm's premises. Cloud VM: a GPU VM (L4/A10 class) typically costs several hundred to >$1,000/month on hyperscalers (no 2026 figures gathered — gap); cheaper pattern is a CPU VM for serving plus a spot GPU for the initial and periodic re-embedding bursts, since embedding is batch work (~10–50 GPU-hours per full pass, see Q2).
Backup/HA posture for a small firm: originals are already in Exchange/SharePoint/file share (the index is a derived artefact), so the realistic target is "rebuildable within N days" plus nightly Postgres backups and Qdrant/OpenSearch snapshots to a second node or S3-compatible store; true HA (3 Qdrant nodes, Patroni Postgres, OpenSearch cluster) triples hardware and ops and is rarely justified for an internal search tool.
OCR budget: if 1–2M of the pages are scans, GPU OCR at ~10–30 pages/s is 10–55 hours; Tesseract on 16 cores at ~1 s/page/core is ~17–35 hours per million pages — either is a one-time load; OCR quality (not speed) is the bigger risk for legal scans.

## Key question 8 — Engineering effort, hidden costs and maintenance

### Takeaway
Vendor and consultancy estimates for a production-grade internal RAG/search system cluster around 6–18 months and ~12–45 person-months from scratch (2–3 months for a v1 with a 2–3 person team), with ongoing maintenance of ~0.3–1.0 senior engineer plus infrastructure; practitioners consistently report that preprocessing/ingestion, document versioning and staleness, chunking, and permission sync — not the vector database — are what take longer than expected. For this firm's scope (Exchange/Graph, SharePoint and SMB connectors; PST handling; deterministic metadata; hybrid search; UI; SSO; MCP; audit) a realistic plan is 4–6 person-months to a usable MVP and 12–20 person-months to production, plus ~0.5 FTE ongoing.

### Cited Findings
- Timelines/effort (vendor-authored, lean toward "buy"): from-scratch production build 6–18 months vs 1–4 months with a platform; ~12–45 person-months ($250k–900k); maintenance ~0.3–1.0 senior engineer + infra — [Kapa.ai, build or buy 2026](https://www.kapa.ai/library/should-you-build-or-buy-an-ai-knowledge-assistant-in-2026); custom builds 26–44 weeks end to end — [CustomGPT build vs buy](https://customgpt.ai/build-vs-buy/); 2–3 months for a production-ready v1 — [Tensoria RAG TCO](https://tensoria.fr/en/blog/rag-project-costs-tco); scenarios from 2 people × 4–6 weeks (basic) to 5 people × 14–18 weeks (enterprise platform) — [RaftLabs RAG development cost](https://www.raftlabs.com/blog/rag-development-cost); 3–8 engineers "sweet spot" — [Zignuts](https://zignuts.com/blog/rag-development-cost-guide); buying moves "retrieval quality, permission sync, and freshness upkeep onto the vendor" — [Brainfish](https://www.brainfishai.com/blog/build-vs-buy-an-ai-knowledge-layer).
- What took longer (practitioners): "the RAG system had no concept of time, and every chunk was equally valid" — superseded policy versions blended into confident wrong answers — [HackerNoon, analytics-team RAG](https://hackernoon.com/i-built-a-rag-system-for-our-analytics-team-it-worked-great-until-we-added-real-data); without versioning, incremental re-indexing and stale-chunk eviction a system "will silently serve outdated information" — [WeGuard Labs, RAG at scale](https://labs.weguard.ai/blog/rag-at-scale-enterprise-lessons); chunking is "perhaps the most underappreciated lesson", semantic chunking beat model swaps — [leaper, production RAG 2026](https://leaper.pages.dev/blog/production-rag-systems-2026); "the real showstopper wasn't performance, but relevance" — [Zartis](https://www.zartis.com/rag-in-the-real-world-lessons-from-production-deployments/); over-engineering across five attempts, "simplicity is often the key to stability" — [dev.to, RAG reality check](https://dev.to/tpacce/rag-reality-check-my-unfiltered-journey-from-zero-to-implementation-and-what-i-learned-4hjc); "RAG is a governance problem" — [Hyperplane](https://thehyperplane.substack.com/p/all-you-know-about-rag-is-a-lie); on an e-mail-archive search tool: "the search isn't great, and there was more preprocessing that I would have liked" — [HN thread mirror](https://hacker-news-clone-eight.vercel.app/item/47966254); 1.3M-PDF ingestion: "the bottleneck wasn't storage — it was AI cost and throughput" — [HN story mirror](https://svelte-hackernews.pages.dev/stories/47025081).
- PST handling: libpff (libyal) reads PST/OST (PFF/OFF) and includes item recovery for corrupted files (unencrypted only) — [libyal/libpff](https://github.com/libyal/libpff); libpst/readpst changelogs record repeated attachment-corruption bugs in older releases and note the PST "password" is stored, not used for encryption — [libpst changelogs on git.kolab.org](https://git.kolab.org/rLIBPSTc6d9b27255c81848b15cfbf1a78ca00474c6452a?diff=1).

- Dedup/threading complexity: e-mail hashes built from multiple metadata fields; attachments as family records; near-dup and threading as separate passes — [GoldFynch](https://goldfynch.com/blog/2025/02/21/understanding-and-managing-different-types-of-duplicates-in-ediscovery.html); [OpenText](https://blogs.opentext.com/what-counts-as-a-duplicate-in-your-ediscovery-software).
- MCP churn: four spec revisions in ~16 months (2025-03-26, 2025-06-18, 2025-11-25, 2026-07-28), with breaking transport changes in the latest — [MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/); [Keycloak compliance table](https://www.keycloak.org/securing-apps/mcp-authz-server).
