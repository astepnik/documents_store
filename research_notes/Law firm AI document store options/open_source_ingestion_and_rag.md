## Key Question 1 — Built-in connectors (SharePoint, Exchange/Outlook, IMAP, Google Drive, local file shares) and their robustness; Onyx in detail

### Takeaway
Onyx (ex-Danswer) is the only fully open-source platform in scope with first-party, incrementally-syncing connectors for SharePoint, OneDrive, Exchange Online (Outlook), Teams, Gmail, Google Drive, IMAP and bulk file upload, plus permission mirroring for the Microsoft/Google connectors — but permission sync, custom user groups and group-scoped document access are Enterprise Edition (paid) features; the MIT Community Edition only offers connector-level "public / private to creator" visibility. No other open-source platform surveyed (RAGFlow, Kotaemon, AnythingLLM, Open WebUI, Dify, Khoj, R2R, Morphik, Nextcloud Context Chat) has an Exchange/Outlook or IMAP connector; most rely on file upload, a handful of SaaS connectors, or an external sync layer (rclone, Airbyte, LlamaIndex readers, Microsoft Graph delta queries).

**Onyx — SharePoint connector (detail)**
- Auth: a client secret is sufficient for indexing only; a certificate credential is required for permission sync. Indexing requires Graph `Sites.Read.All` (or `Sites.Selected` with per-site `read` grants). Permission sync additionally requires `Sites.FullControl.All` (SharePoint permission, not Graph), `GroupMember.Read.All`, `Group.Read.All`, `Directory.Read.All`, `User.Read.All`, `Member.Read.Hidden` — [Onyx SharePoint connector doc](https://raw.githubusercontent.com/onyx-dot-app/documentation/main/admins/connectors/official/microsoft-365/sharepoint.mdx)
- Indexes files in document libraries (including images in them) and site pages (.aspx); scope can be whole tenant or specific sites/libraries/folders. Does NOT index SharePoint lists/list items/attachments; personal OneDrive sites are not indexed unless listed (use the OneDrive connector) — same source
- Incremental sync: after the first run each refresh indexes only changed content; an "Index Documents After" date limits the initial crawl — same source
- Permission sync: document permission sync every 30 min (env `SHAREPOINT_PERMISSION_DOC_SYNC_FREQUENCY`), group sync every 5 min (`SHAREPOINT_PERMISSION_GROUP_SYNC_FREQUENCY`), covers SharePoint site groups and Entra ID groups; sharing-link items treated as private unless "Treat Sharing Links as Public"; Limited Access role ignored. Requires Business/Enterprise on Onyx Cloud or **Enterprise Edition when self-hosted** — same source
- Supported file types: PDF, DOCX, PPTX, EML, EPUB, HTML, XLSX, XLSM, CSV, TSV, TXT/MD/MDX/CONF/LOG/JSON/XML/YML/YAML/SQL, PNG/JPG/JPEG/WEBP. **Legacy DOC, XLS, PPT are not supported ("convert first")**; BMP/TIFF/GIF/SVG/AVIF skipped. Default 20 MB file size limit, self-hosted override via `SHAREPOINT_CONNECTOR_SIZE_THRESHOLD`. Library-name resolution only works on English, German and Spanish tenants (others must use bare site URL). One connector = one tenant — same source

**Onyx — Outlook / Exchange Online connector (detail)**
- Entra app registration, client secret or certificate; **Exchange Online only, on-prem Exchange not supported**. Graph permissions: `Mail.Read`, `User.Read.All`, optionally `GroupMember.Read.All` (mailbox groups) and `Calendars.Read`. By default the app can open every mailbox in the tenant; restrict with an application access policy / Exchange RBAC for Applications (30 min–2 h to apply) — [Onyx Outlook connector doc](https://raw.githubusercontent.com/onyx-dot-app/documentation/main/admins/connectors/official/microsoft-365/outlook.mdx)
- Indexing unit: **one document per thread**, built from the mailbox holding the newest and most messages; each message keeps sender, recipients, date, body; drafts skipped; long threads keep the newest 100 indexable messages drawn from the newest 500. Junk, Deleted Items, Drafts, Outbox, hidden and search folders always skipped — same source
- Attachments (optional): text from supported types appended to the parent message; skips inline images, attached mail items, cloud links, files > 20 MB; caps of 20 attachments per message, 25 download attempts or ~1 million characters per thread — same source
- Incremental sync: each refresh reads messages received since last run and rebuilds threads that gained a message; threads that only lost a message keep stale text until re-index; pruning removes deleted threads — same source
- Permission sync ("Sync with Outlook"): matched by email address; threads visible to owners of all mailboxes holding messages; daily by default (`OUTLOOK_PERMISSION_DOC_SYNC_FREQUENCY`); **requires Enterprise Edition when self-hosted**. Shared mailboxes have no signed-in owner so stay hidden under permission sync unless indexed via a separate Specific-Groups connector; delegate access is not synced — same source

**Onyx — IMAP and File connectors**
- IMAP: one document per email (subject = title, body = text); SSL, port 993 default, username/password or app password; mailbox list optional (empty = all); first run indexes selected emails, each later poll fetches only new emails; **permission sync not supported**; one connector per account; attachments handling not documented — [Onyx IMAP connector doc](https://raw.githubusercontent.com/onyx-dot-app/documentation/main/admins/connectors/official/imap.mdx)
- File connector: upload files or a .zip (unsupported types inside zip skipped); supported: txt/md/mdx/conf/log/json/csv/tsv/xml/yml/yaml/sql, pdf/docx/pptx/xlsx/xlsm/eml/epub/html, png/jpg/jpeg/webp (again no legacy .doc/.xls/.ppt, no .msg). Permission sync does not apply; everyone with connector access sees every file — [Onyx File connector doc](https://raw.githubusercontent.com/onyx-dot-app/documentation/main/admins/connectors/official/file.mdx)

**Onyx — licensing and edition boundaries**
- LICENSE: everything under `backend/ee/`, `web/src/app/ee/`, `web/src/ee/` is under the "Onyx Enterprise License"; third-party components under their own licenses; everything else MIT (Expat). Copyright DanswerAI, Inc. — [Onyx LICENSE](https://raw.githubusercontent.com/onyx-dot-app/onyx/main/LICENSE)

**Onyx — self-host resourcing (current, OpenSearch-based)**
- Lite tier (no document indexing): api_server 1 CPU/1 Gi, web 0.25/512 Mi, postgres 1/1 Gi, nginx, code-interpreter, mcp_server 0.25/256 Mi — ~2.85 vCPU / ~3.4 GiB total; t3.medium-class instance — [Onyx resourcing doc](https://raw.githubusercontent.com/onyx-dot-app/documentation/main/deployment/getting_started/resourcing.mdx)
- Standard tier: api_server 1/2 Gi, celery background workers 2/8 Gi, indexing_model_server 2/4 Gi, inference_model_server 2/4 Gi, postgres 2/2 Gi, **opensearch** 2/4 Gi, nginx; minimum node ~12 vCPU / 24 GB RAM (m7g.xlarge / e2-standard-4..8 / D4s_v3). Using cloud embeddings instead of local reduces model-server memory — same source
- OpenSearch sizing per GB of source text: <5 GB: ~2 GB RAM + 0.25 CPU per GB; 5–50 GB: ~1.5 GB RAM + 0.25 CPU; 50+ GB: ~1 GB RAM + 0.2 CPU per GB. Worked example: 10 GB text → ~19 GB RAM and 4.5 CPU for OpenSearch alone → ≥9 CPU / 35 GB RAM single node (m7g.2xlarge / c5.4xlarge). Index storage ≈ 1.45× source data (0 replicas). JVM heap = 50% of RAM, ≤32 GB. At very large scale a dedicated OpenSearch cluster or managed service is recommended — same source
- [older, Vespa-era] The archived resourcing page said Vespa needs ~3 GB RAM and ~0.5 CPU core per additional 1 GB of indexed documents on top of 4 cores/16 GB, and Vespa stops accepting writes above 75% disk — [docs.onyx.app archive/resourcing via search summary](https://docs.onyx.app/archive/resourcing)
- Search summary of the current docs.onyx.app resourcing page gives "Standard: at least 4 vCPU and 10 GB RAM, 16+ GB preferred" and names OpenSearch — [docs.onyx.app/resourcing via search summary](https://docs.onyx.app/resourcing). This conflicts with the ~12 vCPU/24 GB figure in the GitHub copy; treat the GitHub copy (component-level table) as the more detailed source and flag the discrepancy.

**Sync infrastructure (Microsoft Graph, Airbyte, rclone)**
- Graph driveItem delta: endpoints `/drives/{id}/root/delta`, `/sites/{siteId}/drive/root/delta`, `/users/{id}/drive/root/delta`, `/groups/{id}/drive/root/delta`; start with no params, follow `@odata.nextLink`, persist `@odata.deltaLink`; HTTP 410 Gone → full resync; `token=latest` returns only a fresh deltaLink. Permission-change scanning needs `Sites.FullControl.All` and `Prefer: hierarchicalsharing` / `deltashowsharingchanges` (+ `deltashowremovedasdeleted`, `deltatraversepermissiongaps`) — SharePoint/OneDrive for Business only — [Graph driveitem-delta (v1.0 source)](https://raw.githubusercontent.com/microsoftgraph/microsoft-graph-docs-contrib/main/api-reference/v1.0/api/driveitem-delta.md)
- Graph message delta: `/users/{id}/mailFolders/{id}/messages/delta`, per-folder collection tracking, `Prefer: odata.maxpagesize`, `$filter` only on `receivedDateTime ge/gt`, `$orderby receivedDateTime desc` only, `$search` unsupported, `@removed` entries for deletes/moves — [Graph message-delta (v1.0 source)](https://raw.githubusercontent.com/microsoftgraph/microsoft-graph-docs-contrib/main/api-reference/v1.0/api/message-delta.md)
- A newer admin-level `/admin/exchange/mailboxes/{mailboxId}/folders/{folderId}/items/delta` endpoint exists with `MailboxItem.Read.All` application permission (not for personal accounts) — [learn.microsoft.com mailboxitem-delta (via search summary)](https://learn.microsoft.com/en-us/graph/api/mailboxitem-delta)
- Airbyte Microsoft SharePoint source: runs on Graph, supports Full Refresh on all streams and Incremental on selected streams, needs `Files.Read.All` application permission with admin consent; a separate enterprise-tier "SharePoint Lists" connector uses `lastModifiedDateTime` as cursor — [Airbyte SharePoint connector](https://airbyte.com/connectors/microsoft-sharepoint); [Airbyte SharePoint Lists Enterprise docs](https://docs.airbyte.com/integrations/enterprise-connectors/source-sharepoint-lists-enterprise) (via search summary)
- rclone OneDrive backend: connects to SharePoint sites/document libraries (site search, or drive ID/site ID), supports client-credentials flow with application permissions, `--onedrive-delta` enables delta-based recursive listing (some SharePoint drives only support delta from root), QuickXorHash default since 1.62, limits: 250 GiB/file, 400-char paths, ~100,000 files per folder causes listing errors, custom `--user-agent "ISV|..."` for throttling; Microsoft retires pre-authenticated URLs 2027-04-01 (need rclone ≥1.76) — [rclone onedrive.md](https://raw.githubusercontent.com/rclone/rclone/master/docs/content/onedrive.md)

### Inferences
- For a law firm whose mail lives in Exchange Online, Onyx EE is effectively the only turnkey open-source option with mailbox permission mirroring; a CE deployment can still index the mail (indexing is MIT) but every indexed mailbox becomes visible to everyone with connector access — a confidentiality problem across matters unless one connector per practice group is created and kept "private".
- Onyx's thread-level document model (one doc per thread, newest 100 of 500 messages) is a built-in form of email de-duplication but also means long matter threads are truncated.
- Because Onyx's SharePoint/File/Outlook connectors drop legacy .doc/.xls/.ppt and .msg, a law firm with decades of Word 97-2003 files needs a LibreOffice conversion pre-step (or a Tika/Unstructured sidecar) before Onyx — this is a real gap for legal archives.
- Any non-Onyx platform will require a home-built sync layer: Graph delta queries (both drive and mail), or rclone + a filesystem watcher, feeding the platform's upload API.

## Key Question 2 — Zero / near-zero AI processing at ingest vs. LLM-required ingestion

### Takeaway
Deterministic-only ingestion (text extraction + classical OCR + chunking + embedding) is achievable with Tika, MarkItDown (without llm_client), PyMuPDF/pdfplumber, Tesseract/OCRmyPDF, extract-msg/libpff, and with Onyx, Open WebUI, AnythingLLM, Kotaemon (default loaders) and Nextcloud Context Chat as platforms. Docling, Unstructured hi_res, RAGFlow DeepDoc, Surya and PaddleOCR use small vision models (layout/table/OCR) that are not LLMs but are GPU-hungry; RAGFlow, R2R, Morphik, Kotaemon-GraphRAG, Paperless-AI/GPT and Dify's richer modes add true LLM calls at ingest (metadata extraction, knowledge graphs, RAPTOR, summaries, LLM-OCR) that are optional in most but mandatory in a few.

### Cited Findings

**Deterministic extractors (no model at all)**
- Apache Tika 4.x (Java 17, "over a thousand file types", Apache-2.0, emits Markdown by default as of 4.0.0; Tika 2.x/Java 8 EOL April 2025); tika-app and tika-server modules — [Tika GitHub](https://github.com/apache/tika)
- MarkItDown converts PDF/PPTX/DOCX/XLSX/XLS/HTML/CSV/JSON/XML/ZIP/EPUB/Outlook .msg (`[outlook]` extra) with no model; LLM (`llm_client`) is optional and only used for PPTX/image captions; the `markitdown-ocr` plugin OCRs embedded images only via the LLM and is "silently skipped" without one. Azure Document Intelligence is an optional billable path. A `markitdown-mcp` package exists. Reported >117k GitHub stars (Feb 2026) — [MarkItDown README](https://raw.githubusercontent.com/microsoft/markitdown/main/README.md); [dev.to MarkItDown write-up](https://dev.to/jangwook_kim_e31e7291ad98/markitdown-convert-any-document-to-markdown-for-llms-4bjm)
- PyMuPDF: AGPL-3.0 (commercial license from Artifex); text/dict/HTML/XML/Markdown/JSON output, `find_tables()`, Tesseract OCR integration; claims 10–50× faster text extraction than pure-Python libs (benchmarks unnamed); layout features (`pymupdf-layout`, `pymupdf4llm`) use ONNX Runtime — [PyMuPDF GitHub](https://github.com/pymupdf/PyMuPDF)
- pdfplumber: MIT, built on pdfminer.six, table extraction with lines/text/explicit strategies, no OCR, "works best on machine-generated PDFs"; notes PyMuPDF is "substantially faster" — [pdfplumber GitHub](https://github.com/jsvine/pdfplumber)
- extract-msg (GPL v3, v0.58.2): parses Outlook .msg (OLE2 via olefile), extracts from/to/cc/date/subject/body (HTML/RTF/raw), attachments, embedded .msg, headers, JSON output — [extract-msg README](https://raw.githubusercontent.com/TeamMsgExtractor/msg-extractor/master/README.rst)
- libpff/pypff (LGPL-3.0-or-later, status "alpha", no multithreading): reads PST/OST/PAB in 32-bit ANSI, 64-bit Unicode and 64-bit 4K-page DEFLATE-compressed OST; item recovery — [libpff GitHub](https://github.com/libyal/libpff). A 2021 Stack Overflow report says pypff "seems to read whole file in memory" and libpst "does not seem to be maintained" [older, single-user opinion] — [SO via search summary](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/69905319/how-to-parse-read-outlook-pst-files-with-python)
- libpst/readpst: library + utilities that decode PST and convert to mbox and other formats — [libpst README mirror](https://download.salixos.org/sbo/14.0/libraries/libpst/README). A new pure-Python `pypstreader` positions itself as avoiding libpff's copyleft and native build (self-description, unverified) — [pypstreader on PyPI](https://pypi.org/project/pypstreader/)

**Classical OCR (model-based but not LLM)**
- OCRmyPDF (MPL-2.0): adds OCR text layer / PDF-A, deskew, rotate, multi-core by default (`--jobs`), Tesseract 4.1.1+ engine, >100 language packs, plugins for EasyOCR and PaddleOCR; "battle-tested on millions of PDFs" — [OCRmyPDF GitHub](https://github.com/ocrmypdf/OCRmyPDF)
- PyMuPDF's own ExtractBench (370 PDFs): RapidOCR 85.20% vs Tesseract 78.31% overall; PyMuPDF recommends RapidOCR over Tesseract — [PyMuPDF GitHub](https://github.com/pymupdf/PyMuPDF)
- PaddleOCR 3.7.0 (2026-06-11, Apache-2.0): PP-OCRv6 unified model covers 50 languages (Chinese, English, Japanese + 46 Latin-script); model tiers tiny 1.5M / small 7.7M / medium 34.5M params; reports 5.2× CPU speedup via OpenVINO; PP-StructureV3 converts PDFs/images to Markdown/JSON on CPU or GPU; PaddleOCR-VL-1.6 is a 0.9B VLM (96.3% OmniDocBench v1.6) — [PaddleOCR GitHub](https://github.com/PaddlePaddle/PaddleOCR)
- Surya 2.5 (code Apache-2.0, **weights under modified AI Pubs Open Rail-M: free for research/personal/startups <$5M funding or revenue; broader commercial use needs a paid license**): OCR, layout, tables, 90+ languages; H100+vLLM 4.52 pages/s @192 DPI; Apple M4 Max via llama.cpp 0.19 pages/s (~38.9 s/page); no standalone CPU benchmark; peak RSS ~4.3–4.8 GB on M4 — [Surya GitHub](https://github.com/datalab-to/surya)

**Vision-model parsers (layout/table models, no LLM by default)**
- Docling (MIT code; models have own licenses): layout model, reading order, table structure, formula, image classification, optional VLM (GraniteDocling); formats PDF, DOCX, PPTX, XLSX, HTML, EPUB, Pages/Numbers/Keynote, audio (WAV/MP3), WebVTT, **EML, MSG**, ICS, images, LaTeX, ODF, XBRL, video; outputs Markdown/HTML/JSON/DocTags; Python API, CLI, MCP server, docling-serve — [Docling README](https://raw.githubusercontent.com/docling-project/docling/main/README.md)
- Unstructured open-source library: plain text/HTML/XML/JSON/.eml need no extras; PDFs and images require Tesseract and poppler; MS Office needs libreoffice; file-type detection needs libmagic; vendor-reported table-cell accuracy open-source 0.426 vs paid Transform v2 0.866, adjusted text accuracy 0.715 vs 0.878 (different test sets) — [Unstructured README](https://raw.githubusercontent.com/Unstructured-IO/unstructured/main/README.md)
- RAGFlow 1.0 DeepDoc: "In the 1.0 open-source release, it uses CPU inference for layout analysis, OCR, and table recognition" (Go backend); required model files `det.ort`, `layout.ort`, `tsr.ort`, `rec.ort`, `ocr.res` in `DEEPDOC_MODEL_DIR` — [RAGFlow README](https://raw.githubusercontent.com/infiniflow/ragflow/main/README.md); [RAGFlow FAQ via search summary](https://ragflow.io/docs/faq). [older] v0.20.5 offered `docker-compose-gpu.yml` for GPU DeepDoc/embedding — [RAGFlow docs via search summary](https://najnesnaj.github.io/docs/ragflow/ragflow-gpu-cpu.html)

- R2R (MIT): "Automatic entity & relationship extraction" for knowledge graphs; quick-start requires `OPENAI_API_KEY`, implying an LLM provider is assumed — [R2R README](https://github.com/SciPhi-AI/R2R)
- Morphik (BSL 1.1): ColPali multimodal embeddings at ingest (a vision-language retrieval model, heavier than text embeddings); "rules-processing" metadata extraction (LLM involvement implied by litellm tag, not stated) — [Morphik README](https://github.com/morphik-org/morphik-core)
- Paperless-AI (MIT, **author states "This repo is currently not maintained"**, pending rewrite because Paperless-ngx is adding official AI integration): LLM assigns titles/tags/types/correspondents and offers RAG chat; Ollama/OpenAI-compatible — [paperless-ai README](https://github.com/clusterzx/paperless-ai)
- paperless-gpt (MIT): LLM-generated titles/tags/correspondents/dates; OCR via LLM vision (OpenAI/Ollama/Mistral/Anthropic), Azure DI, Google Document AI, Mistral OCR or self-hosted Docling server; no built-in auth — [paperless-gpt README](https://github.com/icereed/paperless-gpt)
- Nextcloud Context Chat: embeddings via llama.cpp server (CPU or GPU) into pgvector; a text-to-text provider is required for answering but not for indexing; embedding model cannot be changed after install without uninstall/reinstall and empty vector DB — [context_chat_backend README](https://github.com/nextcloud/context_chat_backend); [Nextcloud admin manual via search summary](https://docs.nextcloud.com/server/stable/admin_manual/ai/app_context_chat.html)
- Onyx Standard tier runs separate `indexing_model_server` and `inference_model_server` (embedding/reranking) but no LLM is listed as part of indexing — [Onyx resourcing doc](https://raw.githubusercontent.com/onyx-dot-app/documentation/main/deployment/getting_started/resourcing.mdx)

### Inferences
- A "no-LLM" pipeline for a law firm is realistic: Tika or MarkItDown for Office/HTML/EML/MSG, PyMuPDF or Docling for PDF, OCRmyPDF (Tesseract) or PaddleOCR for scans, libpff/readpst to explode PSTs, then embed with a local model. Docling and RAGFlow DeepDoc add real layout quality but at 5–10× the CPU cost of Tika-style extraction (see Q3 throughput).
- Surya's weight license and PyMuPDF's AGPL are the two licensing traps in the "deterministic" tier for a commercial law firm; Tesseract/OCRmyPDF (MPL), PaddleOCR (Apache), Docling (MIT), Tika (Apache), MarkItDown are clean.
- GraphRAG/RAPTOR/auto-metadata features are everywhere optional; the only platform where some model inference beyond embeddings is unavoidable is Morphik (ColPali) and, in practice, R2R's default config.

### Gaps
- RAGFlow's individual docs for RAPTOR, GraphRAG, auto-keyword/auto-question and tag sets were not opened (only directory listings); whether these are strictly optional at parse time is inferred from the README and metadata page, not confirmed.
- Unstructured's strategy docs (fast/hi_res/ocr_only, detectron2/yolox) were not reachable; stated from README only.
- No published head-to-head accuracy benchmark for Tesseract vs PaddleOCR vs Surya on a shared CPU set was found; one aggregator (codesota) withdrew its own table for mixing methodologies — [codesota](https://www.codesota.com/ocr/best-for-python).

## Key Question 3 — Document-format coverage and quality: Tika vs Docling vs Unstructured vs MarkItDown; CPU throughput

### Takeaway
Tika has the widest format net (incl. legacy binary Office and, through its parsers, mail formats) and the fastest extraction but no layout understanding; Docling has the best open-source PDF layout/table fidelity among MIT tools and now natively reads DOCX/PPTX/XLSX/EML/MSG, at ~1.2–2.5 pages/s on CPU without OCR (≈0.6–1.6 pages/s with OCR on GPU figures given); Unstructured open-source sits between (vendor admits 0.43 table-cell accuracy vs 0.87 for its paid API); MarkItDown is a lightweight Office→Markdown converter (via mammoth/openpyxl) that handles .msg but not legacy .doc. On OmniDocBench-style layout benchmarks, pipeline tools MinerU (0.150) and Marker (0.336) outscore Docling (0.589) and Unstructured (0.586) in one unverified compilation (lower = better).

### Cited Findings

**Format coverage**
- Tika: "over a thousand different file types", Java 17, Markdown output default in 4.x — [Tika GitHub](https://github.com/apache/tika). (PST/MSG via java-libpst is not confirmed on the README page fetched — gap.)
- Docling inputs: PDF, DOCX, PPTX, XLSX, HTML, EPUB, Apple iWork, WAV/MP3, WebVTT, EML, MSG, ICS, PNG/TIFF/JPEG, LaTeX, ODF, XBRL, video, plain text; legacy .doc not listed — [Docling README](https://raw.githubusercontent.com/docling-project/docling/main/README.md)
- MarkItDown: PDF, PPTX, DOCX, XLSX, XLS (`[xls]`), images (EXIF + caption), audio (EXIF + transcription), HTML, CSV/JSON/XML, ZIP, YouTube URLs, EPub, Outlook .msg (`[outlook]`); legacy .doc not mentioned; Python 3.10–3.14; output "may not suit high-fidelity conversion for human reading" — [MarkItDown README](https://raw.githubusercontent.com/microsoft/markitdown/main/README.md). A third-party write-up says XLSX goes through openpyxl → pipe tables and DOCX through mammoth (style→heading mapping) — [dev.to write-up](https://dev.to/jangwook_kim_e31e7291ad98/markitdown-convert-any-document-to-markdown-for-llms-4bjm)
- Unstructured OSS: .eml shown in examples; .msg not mentioned; libreoffice needed for MS Office (which is how legacy .doc/.ppt/.xls get handled); Tesseract + poppler for PDF/images — [Unstructured README](https://raw.githubusercontent.com/Unstructured-IO/unstructured/main/README.md)

- Open WebUI's `:slim` image delegates "document extraction" to external services; search summaries (unverified page) list extraction engines "default, Tika, Docling, Document Intelligence, Mistral OCR, external" — [Open WebUI README](https://github.com/open-webui/open-webui) (engine list is from my own prompt, not confirmed by fetched page — treat as gap)

**Quality benchmarks**
- Docling technical report (arXiv 2408.09869) Table 1: 225-page test set, OCR disabled, two systems; secondary summaries report up to 2.45 pages/s on Apple M3 Max and 1.57 pages/s on Intel Xeon E5-2690, with a lower bound ~0.60 pages/s; M3 Max ≈ 2× Xeon across configs; page images fed at 72 dpi — [Docling Technical Report (arXiv, via search summary; page unreachable)](https://arxiv.org/html/2408.09869v5); [alphaxiv overview](https://alphaxiv.org/overview/2408.09869v5)

- PyMuPDF claims 10–50× faster text extraction and ≥100× faster rendering than pure-Python libraries (unnamed benchmarks) — [PyMuPDF GitHub](https://github.com/pymupdf/PyMuPDF)
- pdfplumber acknowledges PyMuPDF is substantially faster than pdfminer.six/pdfplumber — [pdfplumber GitHub](https://github.com/jsvine/pdfplumber)
- Nextcloud Context Chat: text parsing "is a CPU-bound task so having a powerful CPU will help"; 4+ cores recommended for the embedding model; dedicated machine recommended — [Nextcloud admin manual via search summary](https://docs.nextcloud.com/server/stable/admin_manual/ai/app_context_chat.html)

### Inferences
- Rough CPU planning number for Docling without OCR: ~1.2–2.5 pages/s per 16-thread box → ~100k–200k pages/day/server. 100 GB of mixed legal content (say 5–10 million pages if PDF-heavy) would take weeks on one CPU server with Docling, versus hours-to-days with Tika/PyMuPDF; a single RTX 5090 (7.9 pages/s ≈ 680k pages/day) brings Docling into a few-days range. OCR of scans roughly halves Docling's GPU rate (1.6 pages/s on 5090) — meaning OCR, not layout, is the long pole for scanned archives.

- No reliable docs/hour figure for Tika or MarkItDown was found; both are I/O-bound parsers with no model, so they are plausibly 1–2 orders of magnitude faster than Docling, but this is inference.

### Gaps
- Exact Docling Table 1 numbers (per backend/thread config) not retrievable (arxiv blocked); only secondary summaries.

## Key Question 4 — Metadata (client, matter, handler, case type): storage, rules-based assignment, filtering

### Takeaway
Onyx supports arbitrary key→tag metadata set deterministically via a `.onyx_metadata.json` manifest (zip uploads) or an `ONYX_METADATA=` header line, and lets users filter search/chat by tag; RAGFlow supports typed manual metadata, table-column metadata, pipeline-Transformer metadata and optional LLM-extracted metadata, with retrieval restricted by metadata conditions; Verba (archived) and Cognita (archived) exposed metadata filtering; R2R/Morphik/AnythingLLM/Kotaemon/Open WebUI metadata filtering was not confirmed. No platform surveyed offers a built-in rules engine (folder path, header, sender domain → tag); that logic has to live in a pre-processing step that writes the manifest or calls the API.

### Cited Findings
- Onyx File connector: recognized keys `link`, `title`, `file_display_name`, `primary_owners`, `secondary_owners`, `doc_updated_at`; **any other key becomes a tag**; zip uploads use `.onyx_metadata.json` (array, matched by `filename`); single text files take `#ONYX_METADATA={...}` or `<!-- ONYX_METADATA={...} -->` on line 1; "Users can filter a search or chat by tag, so Onyx reads only documents with that tag" — [Onyx File connector doc](https://raw.githubusercontent.com/onyx-dot-app/documentation/main/admins/connectors/official/file.mdx)
- Onyx also scopes access by connector, document set and user group; service accounts (API keys) inherit group permissions; document sets are managed under "Manage Connectors & Document Sets" — [Onyx Understanding permissions](https://raw.githubusercontent.com/onyx-dot-app/documentation/main/admins/permissions/understanding_permissions.mdx)
- RAGFlow metadata: manual (field name, data type, value), auto-generated via Extractor model (LLM; off by default; built-ins `update_time`, `file_name`), table columns marked Metadata/Both, Transformer component in custom ingestion pipelines; document list filterable by metadata field; "Retrieval can be restricted with metadata conditions"; auto-metadata changes apply only to newly parsed docs (re-parse required) — [RAGFlow metadata_management.md](https://raw.githubusercontent.com/infiniflow/ragflow/main/docs/guides/dataset/metadata_management.md)
- Verba (BSD-3, **archived / "no longer in active development"**) listed metadata filtering, hybrid search, seven chunkers — [Verba README](https://github.com/weaviate/Verba)
- Cognita (Apache-2.0, **archived 2026-03-13, "no longer actively maintained"**) had a Prisma/Postgres metadata store and incremental indexing that skips already-indexed documents — [Cognita README](https://github.com/truefoundry/cognita)
- Morphik advertises "Fast and Scalable Metadata Extraction" (bounding boxes, labeling, classification) via "rules-processing" — [Morphik README](https://github.com/morphik-org/morphik-core)
- Kotaemon organizes files into private/public collections per user — [Kotaemon README](https://github.com/Cinnamon/kotaemon)
- AnythingLLM uses per-workspace document scoping; README does not describe metadata filters — [AnythingLLM README](https://raw.githubusercontent.com/Mintplex-Labs/anything-llm/master/README.md)

### Inferences
- A matter/client taxonomy can be enforced deterministically on Onyx by a pre-ingest script that maps folder paths (e.g. `\\fs\Matters\<ClientID>\<MatterID>\...`) or email headers to tags in `.onyx_metadata.json`, then zips per matter — but this works only for the File connector; the SharePoint/Outlook connectors carry source metadata (site, mailbox) rather than user-defined tags, so matter tagging on those would need folder-per-matter conventions plus document sets.
- RAGFlow's "one dataset per client/matter" plus typed metadata is the alternative pattern; its retrieval-time metadata conditions are usable from the API.

### Gaps
- Whether Onyx SharePoint/Outlook connectors expose path/mailbox/folder as filterable metadata (beyond source and time) was not confirmed.
- R2R, Open WebUI, Dify and AnythingLLM metadata-filter APIs not verified (pages not fetched or not covering it).
- No source found describing a built-in rules engine (folder/header → tag) in any platform.

## Key Question 6 — Pain points at 100 GB+ scale: ingestion time, re-indexing, deduplication

### Takeaway
At 100 GB the dominant costs are (1) search-index RAM (Onyx guidance: ~1 GB RAM + 0.2 CPU per GB of text at 50 GB+, ≈100 GB RAM for the index alone; older Vespa guidance was 3× worse), (2) parse/OCR throughput (1–8 pages/s per Docling worker), and (3) embedding-model lock-in (Nextcloud and Onyx both require a full re-embed when the embedding model changes). None of the platforms surveyed document attachment-level or near-duplicate dedup; Onyx's thread-per-document model handles reply chains, and eDiscovery practice (hash per message + per attachment, MinHash/LSH over quote-stripped bodies, thread "end-of-branch" culling) is the reference technique to implement upstream.

### Cited Findings
- Onyx OpenSearch sizing: 50+ GB of source text → ~1 GB RAM and ~0.2 CPU per GB; index storage ≈1.45× source; recommend dedicated OpenSearch cluster or managed service "at very large scale"; 10 GB text example already needs ≥9 CPU / 35 GB RAM single node — [Onyx resourcing doc](https://raw.githubusercontent.com/onyx-dot-app/documentation/main/deployment/getting_started/resourcing.mdx)
- [older, Vespa era] ~3 GB RAM + 0.5 CPU per GB indexed; Vespa stops writes at 75% disk; GitHub issue #3427 reports Vespa OOM-kills on a 64 GB host, maintainers answering that requirement "depends on document count and size" — [docs.onyx.app archive (via search summary)](https://docs.onyx.app/archive/resourcing); [issue #3427 (mirror, via search summary)](https://github.stncp.dns-dynamic.net/onyx-dot-app/onyx/issues/3427). Danswer's co-founder wrote they chose Vespa after the previous vector DB "struggled at enterprise scale" and that they served "tens of millions of documents per customer" — [Vespa blog](https://blog.vespa.ai/why-danswer-users-vespa/)
- Onyx re-index triggers: Outlook threads that only lost messages keep stale text until re-index; widening the calendar window requires re-index; upgrading to thread documents forces a one-time re-index — [Onyx Outlook doc](https://raw.githubusercontent.com/onyx-dot-app/documentation/main/admins/connectors/official/microsoft-365/outlook.mdx)
- RAGFlow: auto-metadata changes apply only to newly parsed docs; existing docs must be re-parsed; recommended start 4 cores / 16 GB / 50 GB disk, "actual needs depend on document engine, data volume, parsing and concurrency" — [RAGFlow metadata doc](https://raw.githubusercontent.com/infiniflow/ragflow/main/docs/guides/dataset/metadata_management.md); [RAGFlow README](https://raw.githubusercontent.com/infiniflow/ragflow/main/README.md)
- Nextcloud Context Chat: embedding model change requires uninstall, deleting all ExApp data and an empty vector DB; parsing runs in a single non-scalable instance — [Nextcloud admin manual via search summary](https://docs.nextcloud.com/server/stable/admin_manual/ai/app_context_chat.html)
- Docling parse rates: 1.2–1.5 pages/s CPU, 4.2–7.9 pages/s consumer GPU (no OCR); 1.1–1.6 pages/s with OCR on GPU — [Docling gpu.md](https://raw.githubusercontent.com/docling-project/docling/main/docs/usage/gpu.md)
- Vespa feeding guide: write rate cannot exceed storage throughput/IOPS; monitor CPU, memory, disk, network — [Vespa sizing-feeding](https://docs.vespa.ai/en/performance/sizing-feeding.html)
- rclone: folders with ~100,000 files cause SharePoint listing errors; throttling mitigated by custom user agent / own client ID — [rclone onedrive.md](https://raw.githubusercontent.com/rclone/rclone/master/docs/content/onedrive.md)
- Dedup techniques (eDiscovery): hash each message and each attachment, concatenate into a compound hash record, compare attachment hashes for matching/subset relationships (US patents 8458183, 8914331, 7836054); 128-bit hashes can be truncated by corpus size (10698871) — [USPTO 8458183](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/8458183); [USPTO 8914331](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/8914331); [USPTO 10698871](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/10698871)
- Thread culling: collapse a thread to "the end-of-branch email plus any unique attachments"; removing an attachment as a duplicate can leave a message without context — [OpenText eDiscovery blog](https://blogs.opentext.com/what-counts-as-a-duplicate-in-your-ediscovery-software/)
- MinHash + banding (LSH) over tokenized/shingled messages for near-duplicate email at scale, trading some accuracy for performance — [Sublime Security blog](https://sublime.security/blog/how-to-build-fast-similarity-search-for-email-from-the-ground-up/)
- Cognita offered incremental indexing that skips already-indexed documents (but is archived) — [Cognita README](https://github.com/truefoundry/cognita)

### Inferences
- Budget for Onyx at 100 GB text: ≈100 GB RAM + 20 vCPU for OpenSearch plus the 24 GB base, i.e. a 128–192 GB RAM box or a small OpenSearch cluster; disk ≈150 GB index + source cache. Note "100 GB of files" (PST/PDF) is far less than 100 GB of extracted text — PSTs with attachments and scanned PDFs typically yield 10–30% text by size, so the realistic index size is 10–30 GB of text (inference, no source).
- Because Onyx's Outlook connector dedups at thread level and the IMAP connector does not, PST archives should be exploded with libpff/readpst, deduplicated by Message-ID + attachment SHA-256 upstream, and fed as EML (Onyx reads .eml) or MSG→EML (Onyx does not read .msg).
- Embedding-model choice must be final before bulk ingestion on Onyx and Nextcloud; test on a 1–5 GB sample first.

### Gaps
- No practitioner report on actual wall-clock ingestion of ≥100 GB with Onyx or RAGFlow was retrieved (search budget exhausted before the targeted query).
- Onyx's own dedup behaviour for identical attachments across threads or identical files across SharePoint libraries is undocumented in the pages fetched.
- No numbers for re-indexing cost when switching embedding models on Onyx (only that the model servers exist).

## Key Question 7 — Local embedding models for CPU/GPU self-hosting (2026), incl. Polish/German quality

### Takeaway
Qwen3-Embedding (0.6B/4B/8B; 32K context; 1024/2560/4096 dims; MRL; 100+ languages) leads the open MTEB Multilingual board (8B: 70.58; 4B: 69.45; 0.6B: 64.33 vs BGE-M3 59.56 and multilingual-e5-large-instruct 63.22), but on the Polish-specific PIRB benchmark the 2026 ranking is PolDense-1B 64.11 > BGE-Multilingual-Gemma2 63.26 > Stella-PL 62.69 > Qwen3-Embedding-8B 60.93 > Qwen3-Embedding-4B 59.19, so for Polish-heavy corpora a Polish-tuned model or BGE-Multilingual-Gemma2 (9B) is stronger. For CPU-only ingestion, 0.6B-class models (Qwen3-0.6B, BGE-M3, multilingual-e5-large, nomic-embed-text-v2) are the practical ceiling; one indicative comparison puts nomic-embed-text-v2 at ~580 chunks/s on CPU vs ~130 chunks/s for 1024-dim "heavy" models (hardware unspecified).

### Cited Findings
- Qwen3-Embedding spec table: 0.6B (28 layers, 32K seq, 1024-dim), 4B (36 layers, 32K, 2560-dim), 8B (36 layers, 32K, 4096-dim); all MRL-capable and instruction-aware; "over 100 languages" incl. programming languages; MTEB Multilingual mean: 0.6B 64.33, 4B 69.45, 8B 70.58; MTEB English v2: 70.70 / 74.60 / 75.22; comparison rows: gte-Qwen2-7B 62.51, BGE-M3 59.56, multilingual-e5-large-instruct 63.22, gemini-embedding-exp-03-07 68.37 (leaderboard data as of June 2025; arXiv 2506.05176) — [Qwen3-Embedding README](https://raw.githubusercontent.com/QwenLM/Qwen3-Embedding/main/README.md). ### Inferences
- For a Polish+German law firm: Qwen3-Embedding-0.6B (1024-dim, 32K ctx, Apache-2.0) is the best CPU-feasible general multilingual option on MTEB; if Polish recall dominates, BGE-Multilingual-Gemma2 (9B, GPU required) or PolDense-1B score higher on PIRB. German-specific evidence was not found; Qwen3/BGE-M3 cover German within their 100+ languages.
- 8B-class embedders (Qwen3-8B, BGE-Gemma2) need a GPU with ≥16–24 GB VRAM in fp16/bf16 for comfortable batching (inference from parameter count; no source gave VRAM); a single RTX 4090/5090-class card is sufficient; CPU-only runs of 8B models are impractical for 100 GB corpora.
- Dimension choice matters for index RAM: Onyx's ~1 GB RAM per GB text sizing assumes its default embedding size; moving from 1024 to 4096 dims roughly quadruples vector memory (inference).
