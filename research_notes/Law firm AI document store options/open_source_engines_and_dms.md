## KQ1a — Document management systems (family A): license, maturity, maintenance, footprint, feature coverage

### Takeaway
Of the DMS candidates, only Paperless-ngx (GPL-3.0, v3.4.2 Nov 2026, very active, now with Tantivy full-text search, object-level permissions, custom fields, audit log, versions, REST API and built-in LLM/RAG features) and Mayan EDMS (GPL-2.0-only, v4.12.2 Sep 2026) are both actively maintained and lightweight; Alfresco Community (LGPL-3.0, 26.x, Elasticsearch-based community search in 2026) and Nuxeo (Apache-2.0, LTS 2025, JDK 21) are the enterprise-grade options but far heavier and increasingly steered by Hyland's commercial roadmap; Teedy (last release Mar 2023), OpenKM Community (source archived Mar 2026, 7.x binary-only) and Docspell (last stable 0.43.0, early 2025, personal/small-team scope) are weak or stale candidates for a 100 GB+ firm-wide store.

### Cited Findings

**Paperless-ngx**
- License GPL-3.0; the repository shows the `dev` branch with 12,467 commits (very active) — [GitHub paperless-ngx](https://github.com/paperless-ngx/paperless-ngx)
- Latest releases: v3.4.2 (03 Nov), v3.4.1 (31 Oct), v3.4.0 (29 Oct), v3.3.x (Oct), v3.2.x (Sep) — ten releases in ~7 weeks (year inferred 2026) — [GitHub releases](https://github.com/paperless-ngx/paperless-ngx/releases)
- v3.0.0 (released 22 Jul, year inferred 2026) replaced the Whoosh search backend with Tantivy, added "Paperless AI" (LLM suggestions, document chat, an LLM/RAG index whose vector store moved during beta from LanceDB to sqlite-vec), remote OCR via Azure AI, document file versions, a document-parser plugin framework; breaking: dropped Python 3.10, removed API v1 compatibility and API versions <9, removed document/thumbnail encryption — [v3.0.0 release](https://github.com/paperless-ngx/paperless-ngx/releases/tag/v3.0.0); [changelog](https://raw.githubusercontent.com/paperless-ngx/paperless-ngx/dev/docs/changelog.md)
- Feature coverage per official docs: global and object-level permissions (every object has an owner plus view/edit grants to users or groups); custom fields of types Text, Boolean, Date, URL, Integer, Number, Monetary, Document Link, Select; audit trail ("Document History", since 2.7, on by default via `PAPERLESS_AUDIT_LOG_ENABLED`); document versions (metadata on root document, `_vN` version files); workflows with triggers (Consumption Started/Document Added/Updated/Scheduled) and actions incl. webhooks, email, remote OCR, "apply AI suggestions"; mail consumption with OAuth2 for Gmail/Outlook; full-text search over content/title/correspondent/type/tags with boolean operators, field searches, wildcards, date ranges, custom-field queries and optional fuzzy matching; AI features are opt-in and support local (Ollama) or OpenAI-compatible remote models, with a documented warning that document content is sent to the configured provider — [usage.md](https://raw.githubusercontent.com/paperless-ngx/paperless-ngx/dev/docs/usage.md)
- Recent 3.x work explicitly targets query efficiency: prefetching to cut classifier-training queries (3.2.0), faster permission ID sets (3.3.1), fewer permission queries and poppler-based thumbnails (3.4.0), lazy imports to cut idle memory (3.4.1); 3.3.3 "stopped including document content in global search results" — [GitHub releases](https://github.com/paperless-ngx/paperless-ngx/releases)

### Inferences
- Paperless-ngx is the only lightweight DMS candidate whose 2026 feature set already matches most of the requirement list (metadata via custom fields, object-level ACL, audit, versions, REST API, built-in embeddings/RAG); its remaining weaknesses are that the search index (Tantivy) is single-node and not exposed as a general-purpose hybrid engine, and that the LLM index uses sqlite-vec, which is pre-v1 (see KQ1b).
- Mayan EDMS is maintained (4.12.2, Sep 2026) but documentation could not be fetched in this session, so its 2026 feature state (search backends, ACL granularity) is unverified here; its GitHub presence being an abandoned mirror lowers discoverability for AI tooling (no community MCP server was found for it).
- Alfresco Community and Nuxeo bring Elasticsearch/OpenSearch-backed search, CMIS and mature ACL/audit/versioning, but the compose file alone allocates ~8–9 GB of container memory limits before any realistic Elasticsearch heap, and both products' latest work is partly gated in private/commercial repositories.
- Teedy, OpenKM Community and Docspell should be excluded for a firm-scale store on maintenance grounds (Teedy no release since 2023; OpenKM source archived and closed from 7.0; Docspell self-scoped to households/small groups).

### Gaps
- Mayan EDMS feature details (metadata types, indexes, cabinets, Whoosh vs Elasticsearch search backend, ACL model, events) and hardware requirements could not be verified because docs.mayan-edms.com and mayan-edms.com are not reachable from this session; the GitLab README is a landing page only.
- No official Paperless-ngx RAM/CPU sizing table was found; only a third-party vendor table.
- Alfresco Community 25.x/26.x release notes (connect.hyland.com) were not fetchable; component versions are taken from the master compose file instead.
- Whether Hyland's announced open-source "Cloud Content Repository" has shipped, and under which license, was not confirmed.

## KQ1b — Search and vector engines (family B): license, maturity, maintenance, feature coverage

### Takeaway
All engines except Elasticsearch's x-pack features are open-source-licensed and actively released in 2026 (ES 9.5.6, OpenSearch 3.9.0, Solr 10.1.0, Qdrant 1.20.0, Weaviate 1.40.4, Milvus 3.0.5, Typesense 30.2, Meilisearch 1.56.1, pgvector 0.8.7, ParadeDB 0.26.5, LanceDB 0.41.0, Chroma 1.5.9); the licensing traps are Elasticsearch (AGPL/SSPL/ELv2 core but RRF retriever and `bbq_disk` require an Enterprise license), ParadeDB (AGPL-3.0 community, commercial Enterprise), Meilisearch (MIT core, BSL/commercial Enterprise for sharding/search rules), Weaviate (BSD-3 core, commercial `wl/` folder) and Typesense (GPL-3.0 server).

### Cited Findings

**Elasticsearch**
- Source is triple-licensed AGPL-3.0-only / SSPL-1.0 / Elastic License 2.0 by default; code under ELv2 only is "found only in the x-pack folder" — [elasticsearch LICENSE.txt](https://raw.githubusercontent.com/elastic/elasticsearch/main/LICENSE.txt)
- Elastic added AGPLv3 as a license option for Elasticsearch and Kibana on 3 Sept 2024 (some outlets date the announcement Aug 2024) (search summary) — [Admin Magazine](https://www.admin-magazine.com/News/Open-Source-AGPL-Added-as-License-Option-for-Elasticsearch); [IT Brief](https://itbrief.co.uk/story/elastic-reintroduces-open-source-licence-for-elasticsearch-kibana)
- The RRF rank plugin declares `RANK_RRF_FEATURE` as a `LicensedFeature.Momentary` named "rank-rrf" with `License.OperationMode.ENTERPRISE` — i.e. RRF is Enterprise-tier, not free — [RRFRankPlugin.java](https://raw.githubusercontent.com/elastic/elasticsearch/main/x-pack/plugin/rank-rrf/src/main/java/org/elasticsearch/xpack/rank/rrf/RRFRankPlugin.java)
- `dense_vector` index types: `hnsw`, `int8_hnsw` (~4x less memory), `int4_hnsw` (~8x), `bbq_hnsw` (~32x), `bbq_disk` (k-means clustering + binary quantization, "Requires an Enterprise subscription", since 9.2), plus `flat` variants; defaults: 9.0 float → `int8_hnsw`; 9.1+ float ≥384 dims → `bbq_hnsw`; 9.4+ → `bbq_disk` "when your license allows it"; max 4096 dims; HNSW defaults m=16, ef_construction=100 — [dense-vector.md](https://raw.githubusercontent.com/elastic/elasticsearch/main/docs/reference/elasticsearch/mapping-reference/dense-vector.md)
- Latest releases: 9.5.6 and 9.4.9 (02 Nov), 8.19.24 (02 Nov) (year inferred 2026) — [elasticsearch releases](https://github.com/elastic/elasticsearch/releases)
- Elastic's 9.1 blog: BBQ compresses float vectors ~32x and became the default for ≥384-dim dense vectors; Elastic reports BBQ ranking quality better than float32 in 9 of 10 datasets due to reranking a larger candidate pool (vendor claim; search summary) — [Elastic Search Labs 9.1 BBQ/ACORN](https://www.elastic.co/search-labs/blog/elasticsearch-9-1-bbq-acorn-vector-search)

**OpenSearch**
- Apache-2.0; "OpenSearch is a registered trademark of LF Projects, LLC" (Linux Foundation) — [GitHub OpenSearch](https://github.com/opensearch-project/OpenSearch)
- Latest releases 3.9.0 (29 Sep) and 2.19.7 (20 Oct) (year inferred 2026) — [OpenSearch releases](https://github.com/opensearch-project/OpenSearch/releases)
- Hybrid query introduced in 2.11; two combination approaches (score-based normalization: `min_max`, `l2`, `z_score`; rank-based RRF); either via a search pipeline (normalization-processor or score-ranker-processor) or "fusion mode" inline in the `hybrid` query with no pipeline; supports pre-filter (`filter`) and `post_filter` with facets on unfiltered query — [hybrid-search docs source](https://raw.githubusercontent.com/opensearch-project/documentation-website/main/_vector-search/ai-search/hybrid-search/index.md)
- `score-ranker-processor` (RRF) introduced in OpenSearch 2.19; `rank_constant` 1–10000, default 60; per-clause weights must sum to 1.0 — [score-ranker-processor docs source](https://raw.githubusercontent.com/opensearch-project/documentation-website/main/_search-plugins/search-pipelines/score-ranker-processor.md)
- Disk-based vector search introduced 2.17: `mode: on_disk` on `knn_vector` defaults to faiss HNSW, 32x compression (binary quantization), rescoring enabled with `oversample_factor` 2.0; 16x/8x/4x also available (4x uses Lucene engine); only float/half_float — [disk-based-vector-search docs source](https://raw.githubusercontent.com/opensearch-project/documentation-website/main/_vector-search/optimizing-storage/disk-based-vector-search.md)
- From 3.1, `on_disk` with 1x compression activates "memory-optimized search" that loads data on demand (search summary; page not fetched) — [OpenSearch blog](https://opensearch.org/?p=8276); [knn-memory-optimized docs](https://docs.opensearch.org/latest/mappings/supported-field-types/knn-memory-optimized)
- OpenSearch 3.7 expanded the Hybrid Optimizer (Search Relevance Workbench) to z-score and RRF (search summary; page not fetched) — [Instaclustr on OpenSearch 3.7](https://www.instaclustr.com/blog/opensearch-3-7-faster-vectors-and-smarter-hybrid-search/)

**Apache Solr**
- Releases: 10.1.0 (Oct 27, 2026), 9.11.0 (Oct 4, 2026), 10.0.0 (Mar 3, 2026), 9.10.1 (Jan 20, 2026), 9.10.0 (Nov 6, 2025) — [apache/solr tags](https://github.com/apache/solr/tags)
- "Combined Query" (JSON Query DSL) runs multiple queries (e.g. `lucene` + `knn`) and fuses them with RRF (`combiner.algorithm` default `rrf`, `combiner.rrf.k` default 60, `maxCombinerQueries` default 5) via `solr.CombinedQuerySearchHandler` + `solr.CombinedQueryComponent`; limitations: no grouping/cursors; always executes as a distributed search; `numFound` may be a lower bound; in Standalone mode shard URLs must be allow-listed — [json-combined-query-dsl.adoc](https://raw.githubusercontent.com/apache/solr/main/solr/solr-ref-guide/modules/query-guide/pages/json-combined-query-dsl.adoc)
- Solr `DenseVectorField` with `vectorDimension` and `similarityFunction`; a 2026 community post reports production hybrid search with 1024-d vectors (anecdotal; search summary) — [Solr 9.11 guide](https://solr.apache.org/guide/solr/9_11/query-guide/json-combined-query-dsl.html); [opensolr dev.to post](https://dev.to/opensolr/hybrid-search-in-apache-solr-is-now-production-ready-with-1024d-vectors-26i4)

**Vespa**
- Apache-2.0; "The AI search platform" over vectors, tensors, text and structured data; releases cut from master each weekday morning (Mon–Thu), Java 17 for Java-only builds; Vespa Cloud is the hosted option — [GitHub vespa-engine/vespa](https://github.com/vespa-engine/vespa)
- Vespa's HNSW-IF approach stores most vector data on SSD while keeping graph structures in memory (third-party summary of Vespa blog; search summary) — [Vespa blog via plushcap](https://www.plushcap.com/content/vespa/blog/vespa-billion-scale-vector-search-using-hybrid-hnsw-if)
- No 2025 Vespa license change was found in any result; Vespa remains Apache-2.0 per its repository — [GitHub vespa-engine/vespa](https://github.com/vespa-engine/vespa)

**Qdrant**
- Apache-2.0; JSON payload filtering (keyword, full-text, numeric range, geo; must/should/must_not), on-disk vectors with io_uring, built-in quantization "up to 97%" RAM reduction, dense + sparse + multivector, hybrid fusion RRF and DBSF, sharding/replication; default container has no authentication and listens on all interfaces — [GitHub qdrant/qdrant](https://github.com/qdrant/qdrant)
- Releases (year inferred 2026): v1.20.0 (22 Oct: BM25 scoring on the full-text index, TurboQuant turbo8/turbo16, per-element payload indexes, ACORN on m=0 graphs, `inline_storage`), v1.19.0 (05 Aug: 4-bit TurboQuant primary storage, memory tiers cold/cached/pinned, global quota API), v1.18.0 (11 May: TurboQuant, low-memory mode, strict mode), v1.17.0 (20 Feb: relevance feedback, weighted RRF, audit access logging) — [qdrant releases](https://github.com/qdrant/qdrant/releases)
- Memory tiers (since v1.19): dense vectors default `cached` (pinned not allowed), HNSW index default `cached` (cold/pinned allowed), quantized vectors default `pinned` when originals are cached, sparse index `pinned`, payloads `cold`, payload indexes `pinned`, ID tracker `pinned`; guidance: keep HNSW in RAM, pin quantized copy when originals are on disk, use local NVMe/SSD not NAS; an on-disk HNSW index with inline storage "can grow to roughly 3–6 times the float32 vector size" — [memory-tiers.md](https://raw.githubusercontent.com/qdrant/landing_page/master/qdrant-landing/content/documentation/ops-configuration/memory-tiers.md)

**Weaviate**
- BSD-3-Clause for most of the repo; files in `wl/` are commercial-license only (Enterprise features need a license key); hybrid BM25+vector, filtering, multi-tenancy, RBAC, quantization, replication; REST, gRPC and GraphQL APIs; compose example uses image 1.36.0 — [GitHub weaviate/weaviate](https://github.com/weaviate/weaviate)
- Latest v1.40.4 (Nov 5), with parallel patch lines 1.39.x–1.36.x; recent titles are fixes (RBAC, reindex, LSM store performance) (year inferred 2026) — [weaviate releases](https://github.com/weaviate/weaviate/releases)
- Hybrid search: `alpha` 0 (pure BM25) to 1 (pure vector); fusion `relativeScoreFusion` default since v1.24, `rankedFusion` alternative; BM25 operators `or`/`and`/`and_cross` (v1.38.8+); filters apply — [hybrid.md](https://raw.githubusercontent.com/weaviate/docs/main/docs/weaviate/search/hybrid.md)

**Milvus**
- Apache-2.0; modes Lite (pip), Standalone, Distributed (Kubernetes, "tens of thousands of search queries on billions of vectors"); indexes HNSW, IVF, FLAT, SCANN, DiskANN, GPU CAGRA, quantized variants, mmap; full-text BM25, learned sparse (SPLADE, BGE-M3), sparse+dense in one collection, hybrid with rerankers; RBAC, mandatory auth, TLS — [GitHub milvus-io/milvus](https://github.com/milvus-io/milvus)
- Releases: 3.0.5 (Oct 30, 2026), 3.0.4 (Oct 26, 2026, separate sparse AutoIndex params for BM25, lazy column-group loading), 3.0.3 (Oct 14, 2026, Function Chain for Hybrid Search), 3.0.1 (Sep 9, 2026, TEXT field, L1 reranking, weighted RRF); 2.6.x maintenance line (2.6.26 Oct 26, 2026) — [milvus releases](https://github.com/milvus-io/milvus/releases)
- Full-text search: BM25 function maps a VARCHAR field to a `SPARSE_FLOAT_VECTOR`; params `bm25_k1`, `bm25_b`, `inverted_index_algo` (DAAT_MAXSCORE default); one input field per function — [full-text-search.md (2.5.x)](https://raw.githubusercontent.com/milvus-io/milvus-docs/v2.5.x/site/en/userGuide/search-query-get/full-text-search.md)
- DiskANN: float vectors only; L2/IP/COSINE; data path must be on NVMe SSD; memory tuned via `PQCodeBugetGBRatio` and `SearchCacheBudgetGBRatio`; no explicit RAM sizing figures in the doc — [disk_index.md](https://raw.githubusercontent.com/milvus-io/milvus-docs/v2.5.x/site/en/reference/disk_index.md)

### Inferences

## KQ2 — Which engines natively do hybrid search (BM25 + dense with fusion such as RRF) vs needing two systems?

### Takeaway
Native single-engine hybrid with built-in fusion exists today in OpenSearch (score-based or RRF, since 2.11/2.19), Solr (RRF Combined Query), Weaviate (relativeScoreFusion/rankedFusion), Qdrant (RRF/DBSF prefetch fusion, BM25 scoring since 1.20), Milvus (BM25 sparse field + RRFRanker/WeightedRanker), Typesense (alpha-weighted hybrid), Meilisearch (hybrid), Vespa (ranking expressions over BM25 + nearestNeighbor), and Elasticsearch (RRF retriever, but Enterprise-licensed); PostgreSQL (pgvector + tsvector or pg_search) and SQLite (FTS5 + sqlite-vec) do hybrid only by composing two queries and fusing in SQL/app code.

### Cited Findings
- OpenSearch `hybrid` query (introduced 2.11) combines clauses via normalization (min_max/l2/z_score) or RRF; fusion can be declared inline ("fusion mode", no pipeline) or in a search pipeline; pre- and post-filtering supported — [OpenSearch hybrid-search doc source](https://raw.githubusercontent.com/opensearch-project/documentation-website/main/_vector-search/ai-search/hybrid-search/index.md); RRF processor since 2.19 — [score-ranker-processor](https://raw.githubusercontent.com/opensearch-project/documentation-website/main/_search-plugins/search-pipelines/score-ranker-processor.md)
- Solr Combined Query fuses `lucene` + `knn` sub-queries with RRF (k default 60) in one request — [Solr ref guide source](https://raw.githubusercontent.com/apache/solr/main/solr/solr-ref-guide/modules/query-guide/pages/json-combined-query-dsl.adoc)
- Weaviate hybrid = BM25F + vector with `alpha`, `relativeScoreFusion` (default since 1.24) or `rankedFusion` — [Weaviate hybrid.md](https://raw.githubusercontent.com/weaviate/docs/main/docs/weaviate/search/hybrid.md)
- Qdrant: "Hybrid queries merge results through fusion strategies such as RRF and DBSF"; sparse (full-text) vectors supported — [Qdrant README](https://github.com/qdrant/qdrant); v1.17 added weighted RRF; v1.20 added BM25 scoring on the full-text index — [Qdrant releases](https://github.com/qdrant/qdrant/releases)
- Milvus `hybrid_search()` takes one `AnnSearchRequest` per vector field (dense + BM25-generated sparse) and fuses with `RRFRanker` or `WeightedRanker`; default max 4 vector fields per collection (`proxy.maxVectorFieldNum` up to 10) — [Milvus multi-vector-search.md](https://raw.githubusercontent.com/milvus-io/milvus-docs/v2.5.x/site/en/userGuide/search-query-get/multi-vector-search.md)
- Elasticsearch RRF retriever is licensed at `OperationMode.ENTERPRISE` — [RRFRankPlugin.java](https://raw.githubusercontent.com/elastic/elasticsearch/main/x-pack/plugin/rank-rrf/src/main/java/org/elasticsearch/xpack/rank/rrf/RRFRankPlugin.java); a practitioner article describes client-side fusion workarounds and OpenSearch as the free alternative (search summary; page not fetched) — [dev.to RRF on free Elasticsearch](https://dev.to/u11d/reciprocal-rank-fusion-on-free-elasticsearch-licensing-workarounds-and-the-opensearch-alternative-56jk)
- Typesense: hybrid keyword+vector with configurable `alpha` (v0.25.2), re-ranking of single-source hits (v28.0), built-in embedding generation — [Typesense releases](https://github.com/typesense/typesense/releases); [Typesense README](https://github.com/typesense/typesense)
- Meilisearch: "hybrid search that combines semantic and full-text search" — [Meilisearch README](https://github.com/meilisearch/meilisearch)
- pgvector README: hybrid is done by combining pgvector with Postgres full-text search (`plainto_tsquery`, `ts_rank_cd`) and merging via RRF or a cross-encoder in SQL/app — [pgvector README](https://github.com/pgvector/pgvector)
- ParadeDB lists "vector search and hybrid search" as features but vector indexing relies on pgvector; native hybrid "still in development" (search summary) — [ParadeDB README](https://github.com/paradedb/paradedb); [dev.co](https://dev.co/databases/open-source/paradedb)
- Chroma 1.5.9 added sparse search (MaxScore index) to the open-source line; README advertises hybrid for Chroma Cloud — [Chroma releases](https://github.com/chroma-core/chroma/releases); [Chroma README](https://github.com/chroma-core/chroma)
- LanceDB: BM25 FTS combinable with vector search, RRF default reranker (search summary; docs not fetched) — [developersdigest LanceDB](https://www.developersdigest.tech/vector-databases/lancedb)
- SQLite FTS5 + sqlite-vec hybrid "requires running two separate searches and merging results in application code" (search summary) — [dev.to sqlite hybrid RAG](https://dev.to/soytuber/building-a-hybrid-rag-in-200-lines-sqlite-fts5-sqlite-vec-rrf-38h1)

### Inferences
- "Two systems" is only forced on you with pure pgvector (no BM25 ranking beyond ts_rank), with Elasticsearch Basic if you refuse client-side fusion, and with Chroma/sqlite-vec. With Postgres, a single database still suffices (tsvector/GIN or pg_search BM25 + pgvector in one SQL statement with an RRF CTE), so "two systems" becomes "two indexes, one query" — acceptable for agent APIs but with no engine-level tuning of fusion.
- For a law firm, the practical differentiator is whether metadata filters (client, matter, handler, case type) are applied before fusion with good recall: OpenSearch (`filter` pre-filter), Qdrant (payload filter per prefetch, ACORN), Milvus (`expr` per request), Weaviate (filters on hybrid) and pgvector 0.8 (iterative scans) all document this; Solr Combined Query does not document filter interaction and disallows grouping/cursors.

### Gaps
- Vespa hybrid specifics (rank profiles combining `bm25()` and `closeness()`, RRF support) were not verified because docs.vespa.ai was unreachable; Vespa is widely used for hybrid but only the Apache-2.0 license and tensor/text architecture were confirmed from GitHub.
- Qdrant's exact version that introduced the Query API/prefetch fusion was not confirmed (docs page path 404 from GitHub raw).

## KQ3 — Realistic index sizes, memory and latency at 10–50M chunks with 768–1024-d embeddings; HNSW vs disk-based

### Takeaway
Raw float32 vectors alone are 30–41 GB per 10M chunks (768–1024 d) and 150–205 GB at 50M, and in-memory HNSW engines (Weaviate rule of thumb 2x) would need roughly 80–400 GB RAM; quantization (int8/int4/BBQ/TurboQuant/SBQ) and disk-tiered designs (Elastic BBQ/DiskBBQ, OpenSearch on_disk 32x, Qdrant cold vectors + pinned BQ, pgvectorscale StreamingDiskANN, Milvus DiskANN) bring the RAM working set for 10M×1024-d down to the low single-digit GB range at the cost of rescoring I/O and higher tail latency; Qdrant's published 400M-vector run (64 GB RAM, 0.6–2.2 s per query) and Elastic's documented formulas give the only concrete numbers found.

### Cited Findings
- Elastic documented RAM formulas: HNSW graph RAM = `num_vectors × 4 × m`; unquantized float HNSW total = vectors + graph; quantized indexes keep raw floats on disk and the RAM working set is the quantized copy + graph; worked example 1,000,000 × 1024-d float HNSW (m=16) = 4,160,000,000 bytes (~3.87 GB); quantization reduces memory up to 4x (int8), 8x (int4), 32x (bbq) and increases disk by up to 25%/12.5%/3.125%; for dims ≥384 Elastic recommends a quantized index; latency "rises sharply" once the working set no longer fits the page cache; DiskBBQ (ES 9.3+) sizes centroids as `⌈N/384⌉ × (dims+16)` and clusters as `N × 2 × (⌈dims/8⌉+16)` — [Elastic approximate-knn-search guidance](https://raw.githubusercontent.com/elastic/docs-content/main/deploy-manage/production-guidance/optimize-performance/approximate-knn-search.md)
- Weaviate: "Memory usage = 2 * (the memory footprint of all vectors)" rule of thumb; more precise: vector bytes + `maxConnections` links at 8–10 B each (base layer 2×maxConnections); 1M × 384-d float ≈ 1.5 GB raw, ≈ 3 GB rule-of-thumb, ≈ 2.2 GB with maxConnections=64; disk-backed vectors are "much slower"; SSD required, avoid NFS; "HFresh index" offered as disk-based option — [Weaviate resources.md](https://raw.githubusercontent.com/weaviate/docs/main/docs/weaviate/concepts/resources.md)
- Qdrant large-scale tutorial: LAION-400M (400M × 512-d, ~400 GB vectors + ~200 GB payload) on 8 CPU / 64 GB RAM / 1 TB disk using float16 vectors on `cold` tier, binary quantization `pinned`, HNSW m=6 `cached`; estimated 23.84 GB quantized + 17.88 GB HNSW + 12.4 GB ID tracker ≈ 54.1 GB (observed 53.8 GB); upload ~5,000 points/s, indexing ~4,000 points/s; precision@50 75.2% at 0.7 s/query (rescore_limit 1000), 81.0% at 2.2 s (rescore_limit 5000), ~85% at ~0.6 s with m=16 — [Qdrant large-scale-search.md](https://raw.githubusercontent.com/qdrant/landing_page/master/qdrant-landing/content/documentation/tutorials-operations/large-scale-search.md)
- Qdrant 2022 memory article (glove-100, ~1M vectors): all-in-RAM ~1.2 GB at ~795 RPS; vectors mmapped ~625 MB; vectors + HNSW mmapped ran in 135 MB but at 0.33–5 RPS depending on disk (local SSD at 183k IOPS was ~10x faster than a 63k IOPS disk; network disk at 6.4k IOPS "too slow") — [Qdrant memory-consumption.md](https://raw.githubusercontent.com/qdrant/landing_page/master/qdrant-landing/content/articles/memory-consumption.md)
- Qdrant memory-tier guidance: keep HNSW in RAM; if HNSW must be on disk use inline storage with ≤4-bit quantization, where the index "can grow to roughly 3–6 times the float32 vector size" — [memory-tiers.md](https://raw.githubusercontent.com/qdrant/landing_page/master/qdrant-landing/content/documentation/ops-configuration/memory-tiers.md)
- OpenSearch `on_disk` mode: 32x compression default with rescoring (oversample 2.0) for "large memory savings" and "slightly increased search latency"; from 3.1 memory-optimized search loads on demand (search summary) — [disk-based-vector-search](https://raw.githubusercontent.com/opensearch-project/documentation-website/main/_vector-search/optimizing-storage/disk-based-vector-search.md); [OpenSearch blog](https://opensearch.org/?p=8276)
- pgvector: index build much faster if graph fits `maintenance_work_mem` (example 8 GB); indexes need not fit in RAM but perform better when they do; `halfvec` and binary quantization give smaller indexes; parallel build workers configurable — [pgvector README](https://github.com/pgvector/pgvector)
- pgvectorscale (vendor): 50M × 768-d Cohere at 99% recall, 28x lower p95 latency and 16x higher throughput than Pinecone s1, 75% cheaper on EC2; SBQ uses 1 bit/dim at ≥900 dims — [pgvectorscale README](https://github.com/timescale/pgvectorscale); Timescale's April 2025 Qdrant comparison at the same 50M scale claims "significantly higher throughput while maintaining sub-100 ms latencies" (vendor; search summary) — [TigerData blog](https://www.tigerdata.com/blog/pgvector-vs-pinecone)
- Milvus DiskANN requires NVMe for the data path; memory governed by `PQCodeBugetGBRatio`/`SearchCacheBudgetGBRatio`; no absolute figures — [Milvus disk_index.md](https://raw.githubusercontent.com/milvus-io/milvus-docs/v2.5.x/site/en/reference/disk_index.md); a SNIA 2025 talk ran a 1B-vector DiskANN benchmark on 64 GB RAM (search summary) — [SNIA SDC25 deck](https://www.snia.org/sites/default/files/2025-10/SNIA-SDC25-Goncalves-Scaling-RAG-NVME-DISKANN.pdf)
- VectorDBBench (MIT) standard performance cases: Large = 10M at 1024-d and 768-d, 5M at 1536-d; XLarge = LAION 100M × 768-d; metrics QPS, latency, recall, build time; full-text cases (MS MARCO, HotpotQA) added June 2026; leaderboard at zilliz.com/benchmark (numbers not on GitHub page) — [GitHub VectorDBBench](https://github.com/zilliztech/VectorDBBench)
- VDBBench 1.0 (July 2025) streaming test: Elasticsearch surpassed Pinecone in QPS after index optimization but took "significantly longer" to reach that performance (search summary) — [Zilliz VDBBench 1.0 blog](https://zilliz.com/blog/vdbbench-1-0-benchmarking-with-your-real-world-production-workloads)

### Inferences
- Applying Elastic's formula (my arithmetic): 10M × 1024-d float HNSW (m=16) ≈ 41.6 GB RAM working set; int8 ≈ 11 GB; int4 ≈ 5.9 GB; BBQ ≈ 2.1 GB; at 50M multiply by 5 (float ≈ 208 GB, BBQ ≈ 10.5 GB). For 768-d subtract ~25%. These are the orders of magnitude any HNSW-based engine (ES, OpenSearch Lucene/faiss, Weaviate, Qdrant, Milvus HNSW, pgvector) will land in, plus engine overhead (Weaviate's 2x rule, Qdrant's ID tracker ≈ 31 bytes/point in its example).
- Disk-based or heavily quantized configurations are the only way to serve 50M chunks on a typical 32–64 GB self-hosted box; expect p50 latencies in tens of ms for in-RAM quantized HNSW but hundreds of ms to seconds when rescoring from disk at low RAM (Qdrant's 0.6–2.2 s at 400M on 64 GB illustrates the tail).
- For a 100 GB source corpus, 10–50M chunks implies chunks of 2–10 KB of text; the lexical index (BM25) for 100 GB of text will itself be tens of GB (Lucene-based engines typically 20–50% of raw text; not sourced here), so the vector tier is not the only memory consumer.

### Gaps
- No independent third-party benchmark with absolute QPS/latency at exactly 10–50M × 768–1024-d across these engines was accessible (VDBBench leaderboard on zilliz.com blocked; ann-benchmarks not consulted). The Timescale numbers are vendor-run.
- pgvector HNSW index size on disk for 1M–10M × 1024-d vectors (e.g. GB figures and build times) could not be sourced; only qualitative guidance from the README.
- Vespa paged-attribute memory behavior unverified (docs blocked).

## KQ5 — Practitioner reports on Paperless-ngx and Mayan EDMS at 100k–1M documents; known scaling limits

### Takeaway
The largest documented Paperless-ngx deployment found is ~360k documents (target 500k) on 8 vCPU/32 GB with PostgreSQL, where the unfiltered document list took 10–30 s on 2.20.x and hung on 3.0.0-beta before being fixed in 3.0.2; a maintainer stated that installations this large are "not explicitly a goal", and older reports show the auto-classifier failing around 8k–14k documents and 60 s searches on under-sized hardware — so Paperless works at 10^5 documents with effort but is not designed for 10^6; no concrete Mayan EDMS scale reports could be retrieved.

### Cited Findings
- Discussion #13161 (3.0.0-beta-rc2): 360,000 documents, 1,000 tags, 4,989 correspondents, 300 document types; Hetzner CCX33 (8 CPUs, 32 GB RAM) on Kubernetes with CloudNativePG PostgreSQL and Redis; on 2.20.15 the unfiltered overview took ~30 s cold / 10–15 s warm; after upgrade it loaded indefinitely while filtered views (~2,000 docs) took ~3 s; contributor noted Paperless has no DB connection pool by default (`PAPERLESS_DB_POOLSIZE` suggested) and reduced N+1 queries from 64 to 14 for a 50-document list; maintainer shamoon: handling installations this large was "not explicitly a goal"; author "Solved using 3.0.2"; another contributor had tested a 50,000-document instance on an old laptop — [paperless-ngx discussion #13161](https://github.com/paperless-ngx/paperless-ngx/discussions/13161)

### Inferences
- Paperless-ngx's bottlenecks at 10^5 documents are Django ORM list/permission queries (N+1, filesort, `effective_content`) and the scikit-learn classifier, not the Tantivy index; the 3.x series is actively fixing these in response to the 360k report, but the maintainers' stated scope means a firm at 500k–1M documents is operating beyond design intent.
- A 100 GB firm corpus with heavy scanned PDFs likely corresponds to 50k–200k documents (using the vendor's 80–250 GB per 10k scanned contracts vs 10–30 GB per 10k digital PDFs), which sits at the edge of documented Paperless practice.

## KQ6 — Operational complexity: single PostgreSQL (pgvector + full text / pg_search) vs dedicated engines

### Takeaway
A single PostgreSQL with pgvector (+ pgvectorscale for disk-oriented indexes, or ParadeDB pg_search for real BM25/facets) gives one backup/ACL/transaction domain and is sufficient for 10M-scale hybrid search if ~10–40 GB of index can be kept warm, but hybrid fusion, filtered recall (iterative scans), index build memory and the AGPL/Enterprise split of ParadeDB are your responsibility; dedicated engines (OpenSearch, Qdrant, Weaviate, Milvus) deliver native hybrid, quantization/disk tiers, RBAC and official MCP servers but add a second stateful system (Milvus distributed needs Kubernetes; Alfresco's compose already runs Elasticsearch + Kibana + batch indexer + ActiveMQ).

### Cited Findings
- pgvector: hybrid via SQL (tsvector + vector, RRF in app/SQL); iterative index scans (0.8.0) added to fix filtered-query recall; index build memory must be managed via `maintenance_work_mem`; HNSW max 2,000 dims (`vector`) / 4,000 (`halfvec`) — [pgvector README](https://github.com/pgvector/pgvector)
- pgvectorscale: PostgreSQL license; label filtering only via `SMALLINT[]` labels (post-filter for other predicates); parallel builds unsupported with labels; `maintenance_work_mem` default "typically 64MB" must be raised — [pgvectorscale README](https://github.com/timescale/pgvectorscale)
- ParadeDB pg_search: BM25, facets/aggregates, JOINs in Postgres; Community AGPL-3.0, Enterprise commercial; weekly-ish releases (v0.26.0–v0.26.5 between 03 Oct and 04 Nov) — [ParadeDB README](https://github.com/paradedb/paradedb); [releases](https://github.com/paradedb/paradedb/releases)
- Postgres MCP Pro adds read-only "restricted" mode, health checks and index tuning to a single-Postgres stack — [crystaldba/postgres-mcp](https://github.com/crystaldba/postgres-mcp)
- Nextcloud's own RAG feature (Context Chat) chose PostgreSQL + pgvector as its vector store — [context_chat_backend](https://github.com/nextcloud/context_chat_backend); Paperless-ngx chose sqlite-vec after trying LanceDB — [v3.0.0 release](https://github.com/paperless-ngx/paperless-ngx/releases/tag/v3.0.0)
- A 2026 article states the cost advantage of pgvector+pgvectorscale over dedicated services "emerges at 50 million vectors and above" and reverses at smaller scale (secondary; search summary) — [SoftwareSeni](https://www.softwareseni.com/pgvector-pgvectorscale-and-the-postgres-vector-search-stack-explained/)
- Dedicated engines' operational surface: Qdrant single binary/container, sharding + replication, memory tiers, but no auth by default — [Qdrant README](https://github.com/qdrant/qdrant); Weaviate Docker/Kubernetes, replication, RBAC, requires SSD and no NFS — [Weaviate README](https://github.com/weaviate/weaviate), [resources.md](https://raw.githubusercontent.com/weaviate/docs/main/docs/weaviate/concepts/resources.md); Milvus Standalone vs Kubernetes-native Distributed, DiskANN needs NVMe and `aio-max-nr` tuning — [Milvus README](https://github.com/milvus-io/milvus), [disk_index.md](https://raw.githubusercontent.com/milvus-io/milvus-docs/v2.5.x/site/en/reference/disk_index.md); OpenSearch hybrid requires either search pipelines or fusion-mode queries, with pagination limits in fusion mode — [hybrid-search doc](https://raw.githubusercontent.com/opensearch-project/documentation-website/main/_vector-search/ai-search/hybrid-search/index.md); Alfresco Community compose runs repository, Share, Postgres 17, Elasticsearch 8.17 + Kibana, batch indexer, ActiveMQ, transform service, ADF app, control center — [community-compose.yaml](https://raw.githubusercontent.com/Alfresco/acs-deployment/master/docker-compose/community-compose.yaml)
- Elastic's guidance that query latency "rises sharply" once the vector working set leaves the page cache, and its per-file `index.store.preload` tuning, illustrates the tuning burden on JVM/Lucene engines — [approximate-knn-search](https://raw.githubusercontent.com/elastic/docs-content/main/deploy-manage/production-guidance/optimize-performance/approximate-knn-search.md)
- Typesense index is fully in-memory (RAM grows with indexed fields) — [Typesense README](https://github.com/typesense/typesense); Meilisearch sharding is Enterprise-only — [Meilisearch README](https://github.com/meilisearch/meilisearch)

### Inferences
- For 10M chunks, one well-provisioned PostgreSQL node (64–128 GB RAM, NVMe) can hold metadata, ACL tables, tsvector/pg_search BM25 and a quantized/halfvec HNSW or StreamingDiskANN index, and a single SQL statement can apply client/matter/handler filters, fuse BM25 and vector ranks (RRF CTE) and enforce row-level security — the smallest operational footprint and the easiest to audit for a law firm. The costs are DIY fusion/relevance tuning, long HNSW builds, and the AGPL (ParadeDB) or vendor (Timescale) dependencies if BM25/DiskANN are needed.
- At 50M chunks or with heavy concurrent agent traffic, the dedicated engines' quantization/disk tiers and native hybrid are materially simpler to tune than pgvector, but they introduce a second source of truth for ACL metadata that must be synchronized from the DMS/Postgres.
- A pragmatic 2026 architecture suggested by the sources: Paperless-ngx (or Postgres-backed custom ingest) as the system of record for documents, OCR, metadata and object permissions; PostgreSQL as the single index for metadata + BM25 + vectors up to ~10M chunks; OpenSearch or Qdrant added only if scale or hybrid-quality needs exceed that.

### Gaps
- No neutral 2025–2026 operational write-up comparing on-call burden, backup/restore and upgrade pain of pgvector vs Qdrant/OpenSearch was retrievable (search budget exhausted; vendor blogs blocked); conclusions above are inferred from documented feature/requirement lists.
- Row-level security interplay with pgvector HNSW scans (recall under RLS predicates) was not sourced.
